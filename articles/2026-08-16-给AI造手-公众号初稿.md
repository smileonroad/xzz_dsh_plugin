# 我查了一下午的 bug，最后发现是模型在一本正经地给我打工

事情是这样的。

前两天我在折腾一个叫 DeepSeek Harness 的开源项目，简单说，它是给 AI 智能体写插件用的。你想让模型多会一个技能，不用重新训练它，写个插件挂进去就行。听起来很酷对吧，我一开始也是这么想的。

然后我就一脚踩进了泥里。

我的第一个插件特别简单，注册一个叫 helloworld 的命令，用户在输入框敲 /helloworld，它就回一句问候。跟所有编程教程里的第一个程序一样，人畜无害。

结果它就是不干活。

不对，准确地说，它是「看起来在干活，实际上没干活」。

我在网页里敲 /helloworld，菜单里能看到这个命令，点下去也有反应，但界面上什么都没有。就像你按了电梯的按钮，灯亮了，门没开，电梯也没动。

我当时的第一反应是，渲染出问题了。界面收到了结果，但没画出来。于是我开始查前端，查事件流，查 UI 装配，查了一个多小时，把能翻的源码都翻了。

愚钝如我，查了半天愣是没找到毛病。

后来我想起来，这项目所有数据都有日志文件，一行一条，压缩存在磁盘上。我就把日志解压出来，准备看看命令执行到底有没有被记录下来。

第一眼看到的东西，让我整个人愣住了。

日志里躺着四次成功的执行记录，成对出现，command/run 开头，command/done 收尾，工工整整，像两列对齐的账本。这说明命令本身没有问题，跑得比谁都欢。

但最近那一次，也就是用户报「没反应」的那次，画风突变。

没有 command/run，也没有 command/done，取而代之的是一条 user/message，后面跟着一大坨推理过程。

我把那坨推理过程打开，看到了模型自己的内心独白。

「用户输入了 /helloworld，这看起来像是要运行一个斜杠命令，但我收到它的时候，它是一条普通消息，这说明当前运行的 web 进程里，这个命令没有被注册。」

模型在日志里，一本正经地分析，为什么自己会收到这条本不该发给它的消息。

你敢信？？？

我查了一个下午的渲染 bug，结果真相是，命令压根就没注册进去。用户敲 /helloworld，系统一看，不认识这个命令，就当普通聊天文本发给模型了。模型莫名其妙地收到一句 /helloworld，还得硬着头皮分析这是什么意思，然后给我回了一长篇「这个命令似乎没有注册」的说明。

烧了 token，费了算力，最后输出一段用户根本不想看的解释。

这就是「无任何返回」的真相。

不是 UI 坏了，不是渲染坏了，是那双手根本不存在。

---

说到这，得先讲讲 DeepSeek Harness 到底是干嘛的，不然下面的话你会听得一头雾水。

你肯定用过或者听说过 AI 智能体，就是那种能自己干活、自己调用工具的 AI。Claude Code、Codex，都是这个路子。模型不光会聊天，还能读文件、跑命令、上网查资料，像个全能实习生。

问题来了，它凭什么会这些？

不是天生就会的。是有人写了插件，把能力挂进去的。DeepSeek Harness 就是干这个的框架，DeepSeek 官方开源出来的。你写一个插件，注册进去，模型就多了一门手艺。

这里有个特别有意思的区分，我琢磨了很久才品出来。

插件分两种，命令和工具。

命令是给人敲的。用户输入框里打 /helloworld，回车，系统直接执行，不经过模型，不烧 token，瞬间出结果。它的定位是抄近道，把一些确定性的、重复的操作，变成一条斜杠。

工具是给模型调的。模型在思考过程中，觉得「这活儿我干不了，得叫个帮手」，于是它调用工具，工具执行完把结果喂回给模型，模型继续往下想。

一个是人指挥，一个是模型自己指挥自己。

这个区别看着简单，但它是整个智能体生态的骨架。你写插件的时候，每写一个命令，就是在给用户修一条近路，每写一个工具，就是在给模型长一只手。

我当时没意识到这层，只知道埋头写代码。

---

再讲讲我踩的那些坑吧，都是血泪，也都是干货。

第一个坑，报错信息骗人。

我第一个版本的配置文件里，插件路径写的是相对路径，./src/index.ts，看起来人畜无害。结果启动就报错，ERR_MODULE_NOT_FOUND，模块找不到。

我顺着报错去查，发现它找的根本不是我以为的那个位置。

这项目的路径解析有个规矩，相对路径不是相对配置文件，而是相对一个叫 profile 的目录，默认在你系统盘的用户目录底下。也就是说，我以为它去项目里找文件，它实际去 C 盘用户目录底下找，找到天荒地老也找不到。

就像你按着地图找一家店，地图的基准点画错了，你走遍整条街都找不到，最后只能骂一句，这破地图。

解决办法也很有意思，我用了一个叫 junction 的东西，这是 Windows 的目录链接，相当于给目录建了个快捷方式。我把项目目录链接到 profile 目录底下，路径一下就通了。不需要管理员权限，一条命令的事。

第二个坑，热更新是假的。

我改完配置文件，兴冲冲地刷新网页，发现啥变化没有。反复试了好几次，一度以为是自己写错了。

后来才知道，这项目的 web 界面默认禁用热更新，你改完插件配置，必须重启整个 web 进程才生效。

界面没反应，不是 bug，是设计。

这句注释写在他们自己的文档里，我当时看完就想，行吧，这也是一种坦诚。

第三个坑，就是开头那个，最邪门的。命令看起来注册了，菜单里看得见，实际上没注册。这个坑的排查过程让我明白了一件事，调试的时候，别信界面，信数据。

界面是给人看的，它会骗人。数据不会。

---

排查完那个 bug，我把第一个插件收尾，开始写第二个，这次是个工具。

工具的名字叫 sql_check，作用是检查 SQL 语法。模型写了一段 SQL，拿不准对不对，就调这个工具验证一下。

选题是我自己定的，因为最近在用 AI 做数据分析，模型经常生成 SQL，语法错了它自己也不知道。人写 SQL 错了，编译器会告诉你，模型写 SQL 错了，只能靠猜。给它一个检查工具，就相当于给它配了个编译器。

有意思的是技术选型。

按常理，检查 SQL 语法得装个 SQL 解析库，几百兆的依赖包，装完还得处理各种兼容问题。但我翻源码的时候发现，DeepSeek Harness 官方自己的包，用的是 Node 内置的 SQLite 模块，零依赖，开箱即用。

我当场就决定，就它了。

Node 的 SQLite 模块是真实完整的 SQLite 解析器，权威，准确，还不用装任何东西。每次调用新建一个内存数据库，检查完就扔，干净利落，不留任何痕迹。

写这个工具的过程中，有个设计细节让我琢磨了很久，最后想通了，觉得特别妙。

SQL 写错了，工具应该怎么处理？

正常人的直觉是，报错，抛异常。但 DeepSeek Harness 的文档里有一条规矩，说的很清楚，工具抛异常，只应该用于基础设施故障，比如网络断了，数据库挂了。而「SQL 写错了」这种结果，属于正常的业务结果，应该作为正常返回值返回。

我当时看到这条规矩，第一反应是，这有什么差别，反正都是告诉调用方出错了。

后来我想明白了，差别大了去了。

抛异常，是「这台机器坏了」。返回 false，是「结果就是这样」。

对模型来说，这两件事完全不是一个性质。机器坏了，模型不知道怎么办，只能放弃。但 SQL 不合法，是一个可处理的信息，模型收到之后，可以改，可以重试，可以换个写法再试一次。

人写代码调 API，习惯了抛异常这套，因为人懂得「异常」是例外情况。但模型没有这个直觉，它只会根据你给的返回结构往下走。

你给模型设计接口，跟给人设计接口，是两套完全不同的思维。

这也是我这次最大的收获，写插件不是写代码，是替模型思考。

---

顺着这个思路再往深里说一点。

我这次折腾完，最大的感受是，我们正在给 AI 造手。

模型本身没有手，它只能说话。你说的话它听得懂，但它碰不到这个世界。你想让它读文件，它读不了，你想让它查资料，它查不了，它只能眼巴巴地看着你。

但你给它一个工具，它就有了一只手。

给一个读文件的工具，它就能读书，给一个查天气的工具，它就能看天，给一个 SQL 检查工具，它就能自己把 SQL 改对。

你写下的每一行插件代码，都是在决定 AI 这个物种，能摸到世界的哪一部分。

这个想法我越想越觉得后背发凉，也越想越觉得兴奋。

发凉是因为，权力的转移正在悄悄发生。以前，工具是给人用的，软件是给人用的，你决定用它，它才动。现在，工具开始给模型用了，你写的代码，服务的对象从人变成了模型。

兴奋是因为，这件事的门槛，比我想象的低得多。

我这次写插件，没有用到任何高深的东西，就是一个配置、一个入口、一个注册函数，核心逻辑加起来不到一百行。我甚至不用管模型怎么想的，我只管把手造好，模型自己会去用。

就像给一个聪明的小孩准备了一抽屉工具，你不用教他每件怎么用，他自己会翻出来用。

图片

我在想，这可能就是未来程序员的样子。

不写业务逻辑，不给人类造界面，而是给 AI 造手，造工具，造能力边界。你造的每只手好用不好用，直接决定模型在这个世界上能走多远。

这活儿，比给人类写软件，有意思多了。

当然，也可能我想多了。也许过两年，模型连手都能自己长出来，插件这行也没了。但这不妨碍我现在觉得，这事挺酷的。

---

最后回到开头那个 bug。

我查了一下午，最后在日志里看到模型的自言自语，当时觉得又好气又好笑。现在回头想，那个场景其实挺有象征意义的。

模型收到了一条不该发给它的消息，它不知道发生了什么，但它没有骂人，没有放弃，它老老实实地分析，分析完还给出了一篇完整的说明，然后安静地等着。

它连「这是谁的错」都不问。

而那个 bug 的根源，只是一个配置文件里，路径写错了。

一个路径，就能让一个聪明的模型，白白烧掉几万 token，然后对着空气解释。

技术世界里到处都是这种荒诞，人犯一个错，机器用最体面的方式帮你兜底。但你指望它兜底，不如自己把路径写对。

所以说到底，造手的人，得比手细心。

我把这次的经历记下来了，从报错信息到排查思路，从设计哲学到踩坑清单，满满当当。以后谁再问我想不想学写 AI 插件，我就把这篇文章甩给他，然后说一句。

你先把这个 bug 看完，再决定。

毕竟，连模型都在日志里等你，你怎么好意思不认真一点。
