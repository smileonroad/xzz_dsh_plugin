# schedule：定时提醒能力

> 相关代码：`packages/schedule/schedule/src/tools.ts`、`runtime.ts`、`domain.ts`；`docs/subsystems/schedule.md`；[examples/web-schedule/cordis.yml](../../examples/web-schedule/cordis.yml)；[demo/run-schedule.mjs](../../demo/run-schedule.mjs)

前面四个 surface 讲的是「agent 怎么被接进来」，schedule 讲的是「agent 怎么自己记住未来」。它不单独存「有哪些提醒」，只往日志里追加事件，想知道就从头算一遍。最妙的是那个 timer——**agent 不是被闹钟叫醒的，是被操作系统内核叫醒的**。

## 是什么

schedule 给 live root agent 提供三个 Session 级工具（`schedule_create` / `schedule_list` / `schedule_delete`），支持 `after_seconds`（相对延迟）、`at`（绝对时刻）、`every_seconds`（固定间隔）三种定时。核心设计理念只有一句话：

> **提醒状态存在 session 日志里；timer、工具返回值、模型 follow-up 都是这份日志的「可丢弃投影」。**

## 怎么跑通（运行 demo）

schedule 有两种跑法：**挂 web overlay 人工对话**（下），或**独立验证脚本自动跑通「增加 + 运行」**（见本节末）。先看 overlay：

```bash
node demo/run-web.mjs --patch examples/web-schedule/cordis.yml
```

连本地网关时的 url / key / 模型配置机制与 web 篇相同（url 在 run-web.mjs env、key 在根 `.env`、换模型 `--patch demo/model.patch.yml`），这里不重复。

overlay 内容非常短，就两个插件：

```yaml
- insert:
    - id: time-context
      name: '@deepseek-ai/dsh-time-context'
    - id: schedule
      name: '@deepseek-ai/dsh-schedule'
```

time-context 负责把自然语言里的时区交给模型理解；schedule 本身**从不推断时区**（见下）。

### 独立 demo：自动验证「增加 + 运行」

[run-schedule.mjs](../../demo/run-schedule.mjs) 是零依赖的自动验证脚本——本地 spawn 一个挂了 schedule 插件的 jsonrpc 服务器（[demo/schedule.cordis.yml](../../demo/schedule.cordis.yml)，= jsonrpc 组合 + `@deepseek-ai/dsh-schedule`，插件放组合最后保证在前置服务之后加载），一条命令走完两条验证线：

```bash
node demo/run-schedule.mjs "该去买咖啡了" 5 deepseek-v4-flash
```

- **增加**：`session/prompt` 让模型调用 `schedule_create` 创建一个 `after_seconds=5` 的提醒，从事件流里观察到 `schedule/change` create 事件（提醒已写进 session 日志）。
- **运行**：到点后 schedule 投递带 `[SCHEDULE REMINDER]` 安全标记（untrusted reminder content）的 follow-up user 消息，模型响应，观察到第二个 turn 结束。
- 退出码 0 = 两条验证线全过；超时兜底不卡死。

连本地网关前提与 jsonrpc 篇相同：`DEEPSEEK_BASE_URL` 环境变量（bootstrap-only）+ key（环境或 `~/.dsh/.credentials.yaml` 全局凭据）。

#### 执行结果输出（节选）

实跑 `node demo/run-schedule.mjs "该去买咖啡了" 5 deepseek-v4-flash`，事件流里依次出现三条验证线（省略 reasoning-delta 噪音）：

```
✔ 增加：schedule/change create → id=schedule-1
   scheduledAt=2026-09-02T01:39:34.262Z（该次运行的 UTC 创建时刻），提醒内容="该去买咖啡了"
…
[schedule/change] dispatch schedule-1
[session.status] running
[user/message] source=plugin "[SCHEDULE REMINDER]\nPresent reminder_prompt_json to the user"
✔ 运行（投递）：收到 [SCHEDULE REMINDER] follow-up（第 2 个 turn 即将开始）
…
[turn/end #2] reason=completed（follow-up 响应）
=== 验证完成：增加 ✔ 运行 ✔ ===
```

- **增加线**：事件流出现 `schedule/change` create（`id=schedule-1`），提醒已写进 session 日志。
- **投递线**：到点后 `[schedule/change] dispatch`，follow-up 的 `user/message` 带 `source=plugin` 和 `[SCHEDULE REMINDER]` 安全标记（模型把它当未受信任内容呈现，不当新指令执行）。
- **follow-up 线**：第二个 turn 正常结束，脚本最后自报 `=== 验证完成：增加 ✔ 运行 ✔ ===`，退出码 0。

## 代码说明：折叠日志（fold）

这是核心。看 [domain.ts](../../packages/schedule/schedule/src/domain.ts) 的 `foldScheduleEvents`——从空开始，逐条读日志：

```ts
for (const event of events.slice(seedLength)) {
  if (event.type !== 'schedule/change') continue
  switch (change.operation) {
    case 'create':   active.set(change.schedule.id, change.schedule)  // 新增
    case 'delete':   active.delete(change.id)                         // 删除
    case 'dispatch': /* 算出下一次时间，没了就从表里移除 */
  }
}
```

所以它**不单独存"当前有哪些提醒"**，只往 session 日志追加 `schedule/change` 事件（create/delete/dispatch），想知道当前状态就把日志从头读一遍现算出来。

类比记账本：日志是流水账（只记"发生了什么"，只追加不改写），fold 就是"想查余额时把流水从头加一遍"。所以：

- **日志是唯一权威**（durable state），active 列表是随时可重建的投影。
- **可丢弃**：投影丢了不可怕，日志还在就能重算；永远不会"日志和状态对不上"。

## 代码说明：怎么追加（append）

fold 是读的一侧，写的一侧更简单——**追加只有三个入口，全是一个调用** `agent.session.append('schedule/change', ...)`。payload 是带 `version: 1` 的三种 operation 之一：

```ts
// create（schedule_create 工具）
agent.session.append('schedule/change', {
  version: 1,
  operation: 'create',
  schedule: record,      // 完整提醒记录
})

// delete（schedule_delete 工具）
agent.session.append('schedule/change', { version: 1, operation: 'delete', id })

// dispatch（到点交付，timer 触发）
agent.session.append('schedule/change', {
  version: 1,
  operation: 'dispatch',
  id: decision.record.id,
})
```

几个要点：

- **append 只记账、不改状态**。它往 session 日志追加一条 `schedule/change`（create/delete 在 [tools.ts](../../packages/schedule/schedule/src/tools.ts)，dispatch 在 [runtime.ts](../../packages/schedule/schedule/src/runtime.ts)），active 状态从不被直接改，fold 读到这笔记才算出来。
- **payload 严格校验**：必须 `version: 1`，operation 只能是 create/delete/dispatch 三选一，非法即抛错（[domain.ts](../../packages/schedule/schedule/src/domain.ts) 的 decode）。
- **append 是提交点**：工具流程里先 `append` 成功，再做持久化 checkpoint（`preflight` 调 `flushSchedulePersistence`，见 [persistence.ts](../../packages/schedule/schedule/src/persistence.ts)）和 `notifyDurableChange()`——先落库，再对外宣称。checkpoint 失败返回 `persistence_uncertain`，模型必须先用 `schedule_list` 复核、不能相信自己的创建结果。
- **失败 fail loud**：`try { append } catch { return internalError() }`，持久化失败不静默吞掉。
- **没有别的写入路径**：这条事件流只有这三个入口，类型上靠 `SessionEventMap` 声明合并注册 `'schedule/change'`。

## 代码说明：timer 怎么醒

timer（[runtime.ts](../../packages/schedule/schedule/src/runtime.ts) 的 `arm()`）**不是轮询**。它用一次性的 `setTimeout` 睡到最早目标时刻：

```ts
const delay = Math.min(target - now, MAX_TIMER_DELAY_MS)  // MAX = 2^31-1 ≈ 24.8 天
this.timer = setTimeout(() => { this.requestDrive() }, delay)
```

**"醒"的底层来自 Node 事件循环 + 操作系统内核**，不是 DSH 自己的机制：

1. `setTimeout` 把回调登记进 Node 的定时器最小堆，不是真的计时。
2. 进程等待时**不做空转轮询**，而是在事件循环 poll 阶段做一次**阻塞的系统调用**，超时上限恰好等于最近定时器剩余时间（Linux 是 `epoll_wait`，Windows 是 IOCP `GetQueuedCompletionStatus`）。
3. 内核让进程真睡过去（CPU 完全空闲），到点把进程唤醒，回调执行 `requestDrive()`。

醒来后 schedule **重读墙钟**、判 overdue、排 follow-up。这就是设计里"回拨不误事、前跳变 overdue"的底层原因：

- **睡，靠单调时钟**（libuv 定时器用 monotonic clock，只数流逝时间）——系统时间回拨不会提前醒。
- **判 overdue，靠墙钟**（`Date.now()`）——系统时间前跳，醒来发现目标已过，直接变 overdue。

**UTC-only**：schedule 永远只存 UTC（`scheduledAt` 是 RFC 3339 UTC），从不推断浏览器时区或模型 context。natural language 里的时区由 time-context 交给模型，模型必须显式传 offset 或 `time_zone`。

## 交付生命周期（delivery）

- 到点后，overdue 提醒先进 **follow-up 队列**，等 agent **完全 idle** 后才打开一个普通 turn 交付；**从不打断当前对话**。
- 交付的 assistant 输出走普通 transcript，无独立回执、无 schedule 专属 UI。
- **Dispatch = 已入队且已记录**，不代表模型成功或用户已读。
- 时区边界安全：`at` 只接受带 offset 的 RFC 3339 字符串或带显式 `time_zone` 的本地对象，缺 `time_zone`、无 offset、非未来目标都会被拒。

## 使用场景

- 定时/周期提醒 live agent（比如每小时汇报、倒计时后提醒）。
- 需要**持久化**（状态进 session 日志，session 恢复可重放）的定时任务。
- 需要 agent 空闲后再交付、不打断当前对话的场景。

## 特点

- **状态 = 日志投影**：schedule 状态不进独立存储，全部从 session 日志 fold 出来。
- **timer 非轮询**：一次性 setTimeout + 内核唤醒，CPU 零占用等待。
- **单调钟睡觉 + 墙钟判 overdue**：回拨不误事、前跳变 overdue。
- **UTC-only 不推断**：所有时间存 UTC，模型必须显式给时区。
- **空闲后交付**：follow-up 排队等 agent idle，不打断对话。
- **Session-local**：提醒只在原 session live 时准点运行；冷 session 恢复后才处理 overdue（见 package README 的 Known Limitations）。
