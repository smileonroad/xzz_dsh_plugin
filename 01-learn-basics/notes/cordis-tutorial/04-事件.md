## 4.1 为什么需要事件

**理论**（教程原话）：

> 服务支持**直接调用**；**事件**让插件**无需知道有哪些插件正在监听**，就能发出通知。

| | 服务 | 事件 |
|---|---|---|
| 方向 | 调用方 → 提供方（**点对点**） | 发送方 → **任意数量**的监听方（**广播**） |
| 依赖 | 消费方知道**名字**，运行时解析实现 | 发送方**完全不知道**有谁在听 |
| 用例 | 「我要用工具注册表」 | 「发生了一件事，感兴趣的自己处理」 |

harness 用事件处理工具结果、模型请求、审批决定等。

## 4.2 声明、发出、监听

**理论**：事件需要**三件**事 —— 声明（类型）、发出（`emit`）、监听（`ctx.on`）。

### 🧪 验证实验：一个计数服务 + 一个监听方

**📄 文件** `01-learn-basics/examples/cordis-tutorial/04-events/stats.ts`

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    stats: StatsService
  }
  interface Events {                                      // ← 事件声明
    'stats/report'(name: string, count: number): void
  }
}

export class StatsService extends Service {
  private counts = new Map<string, number>()

  constructor(ctx: Context) {
    super(ctx, 'stats')
  }

  bump(name: string) {
    const next = (this.counts.get(name) ?? 0) + 1
    this.counts.set(name, next)
    this.ctx.emit('stats/report', name, next)             // ← 发出
  }
}

export const name = 'stats'

export function apply(ctx: Context) {
  ctx.plugin(StatsService)
}
```

### 三个要点

| 点 | 说明 |
|---|---|
| `interface Events` 合并 | 与 [第 3 章](03-服务.md) `interface Context` 合并**相互对应**；它声明事件名和监听器签名，让 `ctx.emit` / `ctx.on` **都有完整类型** |
| `namespace/action` 命名 | `stats/report`、`agent/request`、`tools/pre-execute` —— 让**扁平的事件命名空间**保持易读 |
| `import type {} from './stats.ts'` | **空类型导入**：不在运行时导入任何东西，只为让 TS 看到声明合并 |

> 🔗 回扣 TS 笔记：`import type {}` 正是本项目里反复出现的写法。在 `agent-default-model` 里也有一行一模一样的 —— `import type {} from '@deepseek-ai/dsh-settings'`，作用完全相同：**加载类型增强，不引入运行时依赖**。

### `ctx.on` 也是 effect

> 因为 `ctx.on()` 属于 effect，监听器会随插件一同消失，**绝不需要手动维护 `removeListener`**。

> 🔗 回扣 [第 2 章的判据表](02-生命周期与-effect.md#26-最重要的实践你已经不需要写-ctxeffect-了)：`ctx.on` 属于「Cordis **认识**的资源」→ 直接用，自动清理。

### 🚧 未实测：监听器随插件自动消失

这条理论（「`ctx.on` 的监听器随插件卸载而自动移除」）**🚧 这是推断，我没有实测**。

手上只有**间接证据**：`03-retrack/` 证明了 consumer 会**整个被卸载又重新加载**。既然 `apply` 会重跑、`ctx.plugin(Consumer)` 只调用了一次，那么卸载时它的监听器必然被清掉了 —— 否则第 2 次 `ctx.plugin` 会看到**重复的监听器**，输出就会变成两行。

**想直接验证的话**：在 `04-events/reporter.ts` 的监听器里加一个调用计数，然后在 `dynamic.ts` 里卸载重挂 `reporter` —— 计数应当**从 1 重新开始**，而不是继续累加。

## 4.3 ⭐ 五种分发模式 + 实测

**理论**：一个事件**怎么被分发**，由**发出方**用哪个方法决定。

| 模式 | 调用 | 语义 |
|---|---|---|
| `emit` | `ctx.emit(name, ...args)` | 同步广播；**不等待也不收集**返回的 promise 与值 |
| `parallel` | `await ctx.parallel(name, ...args)` | 所有监听器**并发**运行，并一同等待 |
| `serial` | `await ctx.serial(name, ...args)` | **顺序**运行并等待；第一个「bail 值」胜出并**停止**后续 |
| `bail` | `ctx.bail(name, ...args)` | `serial` 的**同步**版本 |
| `waterfall` | `ctx.waterfall(name, ...args, next)` | **环绕中间件**，见 [4.6](#46-waterfall转换或短路) |

### 🧪 验证实验：五种模式并排跑一遍

**📄 文件** `01-learn-basics/examples/cordis-tutorial/04-modes/modes.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'm/emit'(x: number): string
    'm/parallel'(x: number): string
    'm/serial': (x: number) => string | undefined
    'm/bail': (x: number) => string | undefined
  }
}

export const name = 'modes-demo'

const wait = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms))

export function apply(ctx: Context) {
  // ── emit：同步广播，不等待、不收集 ──
  ctx.on('m/emit', () => { console.log('     [emit] A 执行'); return 'A' })
  ctx.on('m/emit', () => { console.log('     [emit] B 执行'); return 'B' })

  // ── parallel：并发，一起等待 ──
  ctx.on('m/parallel', async () => { await wait(60); console.log('     [parallel] A 结束（慢）'); return 'A' })
  ctx.on('m/parallel', async () => { await wait(10); console.log('     [parallel] B 结束（快）'); return 'B' })

  // ── serial：顺序执行，首个非 undefined 胜出并停止 ──
  ctx.on('m/serial', () => { console.log('     [serial] A 执行'); return undefined })
  ctx.on('m/serial', () => { console.log('     [serial] B 执行 → 胜出'); return 'B' })
  ctx.on('m/serial', () => { console.log('     [serial] C 执行（不该出现！）'); return 'C' })

  // ── bail：serial 的同步版 ──
  ctx.on('m/bail', () => { console.log('     [bail] A 执行'); return undefined })
  ctx.on('m/bail', () => { console.log('     [bail] B 执行 → 胜出'); return 'B' })
  ctx.on('m/bail', () => { console.log('     [bail] C 执行（不该出现！）'); return 'C' })

  void (async () => {
    console.log('① emit —— 不等待、不收集返回值')
    console.log('   → 返回值:', ctx.emit('m/emit', 1))
    await wait(100)

    console.log('\n② parallel —— 所有监听器并发，一起 await')
    console.log('   → 返回值:', await ctx.parallel('m/parallel', 1))

    console.log('\n③ serial —— 顺序执行，首个非 undefined 胜出')
    console.log('   → 返回值:', await ctx.serial('m/serial', 1))

    console.log('\n④ bail —— serial 的同步版')
    console.log('   → 返回值:', ctx.bail('m/bail', 1))

    process.exit(0)
  })()
}
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/04-modes
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
① emit —— 不等待、不收集返回值
     [emit] A 执行
     [emit] B 执行
   → 返回值: undefined

② parallel —— 所有监听器并发，一起 await
     [parallel] B 结束（快）
     [parallel] A 结束（慢）
   → 返回值: undefined

③ serial —— 顺序执行，首个非 undefined 胜出
     [serial] A 执行
     [serial] B 执行 → 胜出
   → 返回值: B

④ bail —— serial 的同步版
     [bail] A 执行
     [bail] B 执行 → 胜出
   → 返回值: B
```

**结论**（逐条对照）：

| 观察 | 证明了 |
|---|---|
| ① 两个 `[emit]` 都打印，但**返回值是 `undefined`** | `emit` 广播了，但**丢弃**返回值 |
| ② `[parallel] B` 排在 `A` **前面**（B 只等 10ms，A 等 60ms） | ⭐ `parallel` **并发** |
| ② 返回值也是 `undefined` | ⚠️ `parallel` **也不收集**返回值 |
| ③ 返回值 `B`，且 **C 从未执行** | `serial` **短路** |
| ④ 和 ③ 输出一模一样 | `bail` 就是同步版 `serial` |

> ⚠️ **`parallel` 也不返回结果** —— 名字容易让人以为会收集。它只保证「**都跑完**」。

## 4.3b ⭐ 「首个 bail 值胜出」到底什么意思

**理论**：这句话里的 **bail** 被用了**两个词性**，是理解它的主要障碍。

### 代码在做什么

```ts
async serial(...args: any[]) {
  for (const cb of this.dispatch('serial', args)) {
    const result = await cb(...args)
    if (isBailed(result)) return result      // ★ 这一行
  }
}                                            // ← 循环走完，隐式返回 undefined
```

★ 那一行同时做了**两件事**：

1. **`return`** → `for` 循环**立即终止**，后面的监听器**不再执行**
2. **`return result`** → 这个值成为 **`ctx.serial()` 的返回值**

> **「胜出」= 它终止了链条，并且它的值成了最终结果。**

### 「bail」的两层含义

| 词性 | 含义 | 出现处 |
|---|---|---|
| **动词** `bail` | **中途退出**（bail out）、放弃继续 | `ctx.bail(...)` 方法名 |
| **名词**「a bail value」 | 「**一个会导致中途退出的返回值**」 | `isBailed()` 的文档 |

`isBailed(v)` 直译就是「**v 是不是一个会导致退出的值**」。

### 🧪 验证实验：审批流

declare module '@deepseek-ai/cordis' {

**结论**（两条，都对上了）：

| 观察 | 证明了 |
|---|---|
| 场景 A：**审批人丙从未出现** | ⭐ 乙一表态，链条**当场终止** |
| 场景 A 返回值 = `REJECTED`（不是 `APPROVED`） | ⭐ **第一个**表态的说了算，不是最后一个 |
| 场景 B：三个人都被问了，返回值 `undefined` | `for` 循环走完，**隐式返回 undefined** |

### 最好的类比：**审批流**

| 监听器返回 | 含义 |
|---|---|
| `undefined`（或 `null`/`false`） | 「**我不表态**，转给下一个人」 |
| 任何其他值 | 「**我拍板了**，就这么定」→ 流程**终止** |

**「首个 bail 值胜出」= 第一个明确表态的人说了算，后面的人不用再问了。**

### ⭐ `serial` 的两种用法（第二种藏着坑）

| 用法 | 写法 | 关注点 |
|---|---|---|
| **① 取决策值** | `const verdict = await ctx.serial(...)` | 用返回值 |
| **② 顺序执行 + 等待** | `await ctx.serial(...)` | **丢弃返回值** |

**harness 用的是第 ② 种** —— `packages/core/agent-loop/src/agent.ts:316`：

```ts
await this.dispatch.serial('agent/turn-stopping', { turn, signal })
//                                             ↑ 返回值被丢弃
```

监听器都是这个形状（`agent-loop/tests/loop.spec.ts:1096`）：

```ts
ctx.on('agent/turn-stopping', ({ agent: subject }) => {
  if (steps < 3) {
    subject.steer(...)      // ← 副作用：往 inbox 塞一条消息
  }
})                          // ← 没有 return → undefined → 不会短路 ✅
```

> ⚠️ **但坑仍然存在**：即使在用法 ② 里，**短路是真实发生的**。
>
> 如果某个 `turn-stopping` 监听器不小心 `return 0` 或 `return ''`，**后面所有监听器都会被静默跳过** —— 返回值虽然被丢弃，**短路副作用不会消失**。
>
> 这些监听器「故意不 return」不是随意的风格，是**必须**的纪律。

## 4.4 ⭐ 源码印证：每种模式到底做了什么

`vendor/cordis/src/events.ts:183-222`：

```ts
// parallel —— 并发 + 聚合错误，但【不返回结果】
async parallel(...args: any[]) {
  const results = await Promise.allSettled(this.dispatch('emit', args).map(async cb => cb(...args)))
  const errors = results.filter((result): result is PromiseRejectedResult => result.status === 'rejected')
  if (errors.length) throw new AggregateError(errors.map(error => error.reason))
}                                          // ← 没有 return！

// emit —— 同步广播，promise 直接丢弃（fire-and-forget）
emit(...args: any[]) {
  this.dispatch('emit', args).map(cb => cb(...args))
}                                          // ← 没 await，没 return

// serial —— for...of + await = 严格顺序
async serial(...args: any[]) {
  for (const cb of this.dispatch('serial', args)) {
    const result = await cb(...args)       // ← 一个一个等
    if (isBailed(result)) return result    // ← 胜出即停
  }
}

// bail —— serial 去掉 await
bail(...args: any[]) {
  for (const cb of this.dispatch('bail', args)) {
    const result = cb(...args)             // ← 没有 await
    if (isBailed(result)) return result
  }
}
```

### 🧪 验证实验：`parallel` 到底等什么

**📄 文件** `01-learn-basics/examples/cordis-tutorial/04-parallel/parallel-waits.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'p/all': (x: number) => Promise<void>
    'p/fireforget': (x: number) => void
  }
}

export const name = 'parallel-waits'

const wait = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms))
const t0 = Date.now()
const stamp = () => `+${String(Date.now() - t0).padStart(3, ' ')}ms`

export function apply(ctx: Context) {
  // ── 实验 1：最快的那个抛错，parallel 还会等慢的吗？ ──
  ctx.on('p/all', async () => { await wait(60); console.log(`   ${stamp()}  A 完成（慢，60ms）`) })
  ctx.on('p/all', async () => { await wait(10); console.log(`   ${stamp()}  B 抛错（快，10ms）`); throw new Error('B 炸了') })
  ctx.on('p/all', async () => { await wait(30); console.log(`   ${stamp()}  C 完成（中，30ms）`) })

  // ── 实验 2：监听器内部 fire-and-forget 的任务，parallel 会等吗？ ──
  ctx.on('p/fireforget', () => {
    void (async () => {
      await wait(80)
      console.log(`   ${stamp()}  内部异步任务完成（此时 parallel 早就返回了）`)
    })()
  })

  void (async () => {
    console.log('① B 最快抛错 —— parallel 还会等 A(60ms) 和 C(30ms) 吗？')
    console.log(`   ${stamp()}  调用 parallel`)
    try {
      await ctx.parallel('p/all', 1)
      console.log(`   ${stamp()}  parallel 正常返回`)
    } catch (error) {
      console.log(`   ${stamp()}  parallel 抛出: ${(error as Error).constructor.name}`)
    }

    console.log('\n② 监听器内部 fire-and-forget —— parallel 会等那个内部任务吗？')
    console.log(`   ${stamp()}  调用 parallel`)
    await ctx.parallel('p/fireforget', 1)
    console.log(`   ${stamp()}  parallel 返回 ← 此刻内部任务还没做完`)

    await wait(120)
    console.log(`\n   ${stamp()}  全部结束`)
    process.exit(0)
  })()
}
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/04-parallel
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
① B 最快抛错 —— parallel 还会等 A(60ms) 和 C(30ms) 吗？
   +  1ms  调用 parallel
   + 16ms  B 抛错（快，10ms）
   + 31ms  C 完成（中，30ms）
   + 66ms  A 完成（慢，60ms）
   + 67ms  parallel 抛出: AggregateError

② 监听器内部 fire-and-forget —— parallel 会等那个内部任务吗？
   + 67ms  调用 parallel
   + 67ms  parallel 返回 ← 此刻内部任务还没做完
   +147ms  内部异步任务完成（此时 parallel 早就返回了）

   +194ms  全部结束
```

**结论** —— 「等待」的三层精确含义：

| 层 | 含义 | 实验证据 |
|---|---|---|
| ① 等的是 **settle**，不是「成功」 | 用的是 `allSettled` 而非 `all` | B 在 **+16ms** 就失败了，`parallel` 一直等到 **+66ms**（A 跑完）才抛出 |
| ② 失败**不中断**等待 | 其余监听器继续跑完 | B 失败后，C（+31ms）和 A（+66ms）**照常完成** |
| ③ 只等**第一层** | 只等 `cb(...args)` 返回的那个 promise | 实验②：`parallel` 在 **+67ms** 返回，内部任务 **+147ms** 才完成 —— **没等** |

```ts
const results = await Promise.allSettled(this.dispatch('emit', args).map(async cb => cb(...args)))
//                 ↑ allSettled                ↑ 只等 cb() 直接返回的 promise
```

| | `Promise.all` | `Promise.allSettled`（parallel 用的） |
|---|---|---|
| 某个 reject 时 | **立即** reject，不等其余 | **继续等**其余全部 settle |
| 何时抛出 | 第一个失败时 | **全部结束后**打包成 `AggregateError` |

### ⚠️ 实战保证与不保证

| 保证 | 不保证 |
|---|---|
| ✅ 所有监听器**函数**都已 settle | ❌ 监听器**内部** fire-and-forget 的任务已完成 |
| ✅ 任一失败都会以 `AggregateError` 浮现 | ❌ 失败会中断其他监听器 |
| ✅ 全部并发 | ❌ **完成顺序确定**（顺序不确定） |
| | ❌ 有超时 —— **一个监听器挂住 = 全体挂住** |

在 harness 代码里，监听器若要把「我还在忙」传达给 `parallel`，**必须 `return` 那个 promise**：

```ts
ctx.on('some/event', async () => {
  await doWork()          // ✅ 隐式返回 promise，parallel 会等
})

ctx.on('some/event', () => {
  void doWork()           // ❌ parallel 以为它已经完成了
})
```

> ⭐ 实验②就是这个 `void doWork()` 的实证：`parallel` 在 **+67ms** 就返回了，而任务到 **+147ms** 才做完 —— **相差 80ms**，正是那个 `wait(80)`。

### 两个容易忽略的行为差异

**① `parallel` 会抛 `AggregateError`**

只要**任何一个**监听器抛异常，`parallel` 就把所有异常打包成 `AggregateError` **抛出** —— 也就是说，`await ctx.parallel(...)` 可能 reject。

而 `emit` **不会** —— 异步监听器的异常会变成 **unhandled rejection**，静默地在别处炸。

**② `emit` 是 fire-and-forget**

`emit` 不 await，所以异步监听器里的异常**不会被调用方捕获**。这是 harness 代码里一个真实的坑。

## 4.5 ⭐ 陷阱：`isBailed` **不是** falsy 检查

**理论**：教程表格说「第一个非 `null`/`false`/`undefined` 返回值胜出」。这句话读快了容易理解成「falsy 值不算」。**看源码**（`events.ts:7-15`）：

```ts
/**
 * @returns `true` unless `value` is `null`, `false`, or `undefined`.
 */
export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
```

**这是三个精确的恒等比较，不是 falsy 判断。**

### 🧪 验证实验：`0` / `''` / `null` / `false` 谁短路

**📄 文件** `01-learn-basics/examples/cordis-tutorial/04-bail-edge/bail-edge.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'e/zero': (x: number) => unknown
    'e/empty': (x: number) => unknown
    'e/null': (x: number) => unknown
    'e/false': (x: number) => unknown
  }
}

export const name = 'bail-edge'

export function apply(ctx: Context) {
  const pair = (event: 'e/zero' | 'e/empty' | 'e/null' | 'e/false', value: unknown, label: string) => {
    ctx.on(event, () => value)
    ctx.on(event, () => { console.log(`     ⚠️  第二个监听器执行了 —— 说明 ${label} 没有短路`); return 'second' })
  }

  pair('e/zero', 0, '0')
  pair('e/empty', '', "''")
  pair('e/null', null, 'null')
  pair('e/false', false, 'false')

  console.log('判据：isBailed(v) = v !== null && v !== false && v !== undefined\n')

  console.log("① 首个监听器返回 0         → ctx.bail 返回:", ctx.bail('e/zero', 1))
  console.log("② 首个监听器返回 ''        → ctx.bail 返回:", JSON.stringify(ctx.bail('e/empty', 1)))
  console.log("③ 首个监听器返回 null      → ctx.bail 返回:", ctx.bail('e/null', 1))
  console.log("④ 首个监听器返回 false     → ctx.bail 返回:", ctx.bail('e/false', 1))
}
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/04-bail-edge
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
判据：isBailed(v) = v !== null && v !== false && v !== undefined

① 首个监听器返回 0         → ctx.bail 返回: 0
② 首个监听器返回 ''        → ctx.bail 返回: ""
     ⚠️  第二个监听器执行了 —— 说明 null 没有短路
③ 首个监听器返回 null      → ctx.bail 返回: second
     ⚠️  第二个监听器执行了 —— 说明 false 没有短路
④ 首个监听器返回 false     → ctx.bail 返回: second
```

### 📖 怎么读这段交错输出

第一次看会觉得行序乱了。其实**顺序完全正确** —— `console.log` 的参数**先求值再打印**：

| 行 | 发生了什么 |
|---|---|
| `① … 0` | 求值时 `ctx.bail('e/zero')` **立刻短路**，第二个监听器**没跑** → 无 ⚠️ |
| `② … ""` | 同上，`''` 也短路了 |
| `⚠️ … null 没有短路` | ⭐ 这行是**③ 的求值过程**打印的 —— 它出现在 ③ 那行**之前** |
| `③ … second` | 求值结束后才打印 ③ 这行 |
| `⚠️ … false 没有短路` | ④ 的求值过程 |
| `④ … second` | ④ 的结果 |

**所以 ⚠️ 行和它所属的编号是「前一行」（⚠️ 在编号行之前）**，不是「后一行」。

### 结论表

| 返回值 | falsy? | 会短路吗？ | 实验证据 |
|---|---|---|---|
| `undefined` | ✅ | ❌ 继续 | 4.3 的 `serial` A |
| `null` | ✅ | ❌ 继续 | ③ 出现 ⚠️ |
| `false` | ✅ | ❌ 继续 | ④ 出现 ⚠️ |
| `0` | ✅ | ✅ **短路** ⚠️ | ① 无 ⚠️，返回值就是 `0` |
| `''` | ✅ | ✅ **短路** ⚠️ | ② 无 ⚠️，返回值就是 `""` |
| `NaN` | ✅ | ✅ **短路** ⚠️ | 同上原理（`NaN !== null` 等三条全成立） |
| `'x'` / `{}` / `true` | ❌ | ✅ 短路 | 4.3 的 `serial` B 返回 `'B'` |

> ⚠️ **实践警告**：想表达「我没意见，继续」时，必须返回 **`undefined`**。
>
> 如果监听器返回 `0`、`''` 或 `NaN`（很自然 —— 比如「计数为 0，所以我不处理」），会**意外吞掉整条链的后续**。

## 4.6 waterfall：转换或短路

**理论**：waterfall 是**实现拦截**的模式。

```ts
ctx.waterfall('demo/transform', 'hello', async () => 'hello')
//                                   ↑ 参数        ↑ 最内层默认逻辑（next）
```

每个监听器收到 `(参数..., next)`：

- 可以**转换** `next()` 的返回值
- 也可以**不调用 `next()` 直接返回** → **短路**（Cordis 文档称之为**否决 veto**）

### 🧪 验证实验：包装 + 短路

**📄 文件** `01-learn-basics/examples/cordis-tutorial/04-waterfall/waterfall-demo.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'demo/transform'(input: string, next: () => Promise<string>): Promise<string>
  }
}

export const name = 'waterfall-demo'

export function apply(ctx: Context) {
  // Listener 1: wrap the downstream result.
  ctx.on('demo/transform', async (input, next) => {
    const downstream = await next()
    return downstream.toUpperCase()
  })

  // Listener 2: short-circuit when it owns the decision.
  ctx.on('demo/transform', async (input, next) => {
    if (input.includes('blocked')) return '** blocked **'
    return next()
  })

  void (async () => {
    console.log(await ctx.waterfall('demo/transform', 'hello', async () => 'hello'))
    console.log(await ctx.waterfall('demo/transform', 'blocked words', async () => 'blocked words'))
  })()
}
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/04-waterfall
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
HELLO
** BLOCKED **
```

**结论**：

| 第一行 `HELLO` | 第二行 `** BLOCKED **` |
|---|---|
| 监听器 1 → `next()` → 监听器 2 → `next()` → 最内层 | 监听器 1 → `next()` → 监听器 2 **直接 return** ✂️ |
| 一路返回，最内层的 `'hello'` 被 2 原样传回、被 1 转大写 | 最内层（`async () => 'blocked words'`）**从未运行** |
| 结果是 `'hello'.toUpperCase()` | 2 返回的 `'** blocked **'` 被 1 转成 `'** BLOCKED **'` |

⭐ **注意第二行的大写**：它证明**监听器 1 的包装逻辑在最外层生效** —— 即使内层短路了，外层的转换照样执行。

### 第二行的执行过程（教程原话）

> 监听器 1 先运行并调用 `next()`，从而调用监听器 2；监听器 2 看到 `blocked` 后**直接返回而不调用 `next()`**，因此**最内层默认逻辑**（传给 `ctx.waterfall` 的函数）**从未运行**；返回途中，监听器 1 再把替换消息转换为大写。

画成图：

```
监听器1 ──next()──▶ 监听器2 ──next()──▶ 最内层默认逻辑
   │                     │                      │
   │                 直接 return ✂️              │
   │◀──────── '** blocked **' ◀────────────────┘
   │
 return '** BLOCKED **'
```

### ⭐ 由此得到一项纪律（本仓库常设规则）

> **只负责观察或标注的 waterfall 监听器必须调用 `next()`**；不调用就直接返回代表**有意短路**。
>
> 如果日志监听器忘记调用 `next()`，会**悄无声息地吞掉所有下游的默认行为**。

这是本仓库的**常设规则** —— 因为这种 bug **没有任何报错**，只是功能"莫名其妙不生效"。

> 🧪 **你可以自己造这个 bug**：把 `waterfall-demo.ts` 里监听器 2 的 `return next()` 删掉（改成什么都不返回），再跑一遍。
>
> 我预期第一行会从 `HELLO` 变成 `UNDEFINED`（因为 `next()` 没被调用，返回值是 `undefined`，再被 `.toUpperCase()` 调用就会 TypeError 或得到意外结果）—— **但这是推断，我没有实测**。留给你验证。

### harness 里的 waterfall

harness 用 waterfall 处理**协作插件可以包装或回答**的决策：

| 事件 | 作用 |
|---|---|
| `agent/request` | 允许插件**替换模型调用配置** |
| `approval/request` | 允许策略**代替用户作答** |

> 🔗 **回扣 architecture.md L105**：
>
> > `agent/pre-step`、`agent/request`、`llm/stream` 和三个 `tools/*` 事件是 **waterfalls**，其监听器**必须调用 `next()`** 才能委托；`agent/turn-stopping` 是 **serial** 且没有 `next()`。
>
> 现在你知道这句话的**完整含义**了 —— 而且知道了忘记 `next()` 的后果是**静默吞掉下游**。

## 4.7 自测

**Q1**：我想在每次工具调用后**记一条日志**，但**绝不改变任何行为**。该用哪种模式？注册时要注意什么？

<details>
<summary>参考答案</summary>

先看这个事件**已经是哪种模式** —— 模式是**事件约定的一部分**，你不能自己选。

- 如果它是 `emit`（如 `stats/report`）→ 直接 `ctx.on`，随便返回什么都行（`emit` 不收集）
- 如果它是 **waterfall**（如 `tools/post-execute`）→ `ctx.on` 后**必须调用 `next()` 并返回它的结果**：

```ts
ctx.on('tools/post-execute', async (call, result, next) => {
  logger.info('tool done', call.name)
  return next()      // ← 绝不能忘！
})
```

**忘了 `next()` = 静默吞掉所有下游行为**，而且没有任何报错。

**自己验证**：跑 `04-waterfall/` 看 `next()` 是怎么串起三层的，再对比 4.6 那道「把 `next()` 删掉」的思考题。

> 🔗 这也解释了 architecture.md 里 `tools/*` 事件为什么特别强调「必须调用 `next()`」—— 日志/遥测类监听器是最容易犯这个错的地方。

</details>

**Q2**：下面的监听器会短路吗？

```ts
ctx.on('some/waterfall', (input, next) => {
  const count = countMatches(input)
  if (count === 0) return 0        // 「没有匹配，我不处理」
  return next()
})
```

<details>
<summary>参考答案</summary>

**会短路！** 而且在 `count === 0` 时 —— 也就是最应该「继续让别人处理」的时候。

`isBailed(0)` → `0 !== null && 0 !== false && 0 !== undefined` → **`true`** → 短路。

正确写法是返回 `undefined`：

```ts
if (count === 0) return undefined   // ✅ 或者直接 `return`
return next()
```

**自己验证**：`04-bail-edge/` 的第 ① 行就是这个判据的直接证明 —— 返回 `0` 时第二个监听器**从未执行**（没有 ⚠️）。

**这是本仓库里最隐蔽的一类 bug** —— 不报错、不崩溃，只是下游的默认行为**凭空消失**。

</details>

**Q3**：`emit` 和 `parallel` 都不返回监听器的结果，它们的关键区别是什么？

<details>
<summary>参考答案</summary>

| | `emit` | `parallel` |
|---|---|---|
| **是否等待** | ❌ 不等（fire-and-forget） | ✅ 等所有监听器结束 |
| **异步异常** | 变成 **unhandled rejection**，在别处静默炸 | 打包成 `AggregateError` **抛出** |
| **能否确定「已完成」** | ❌ 不能 | ✅ 能 |

**关键区别：`emit` 不保证「广播完成时工作已做完」，`parallel` 保证。**

**自己验证**：`04-parallel/` 的实验②证明 `parallel` 会等「第一层 promise」（+67ms 返回）；把同样的监听器换成 `ctx.emit` 再跑，你会看到主流程**在监听器完成前就继续了**。

所以：

- 只是**通知**（有监听器就处理，没就算）→ `emit`
- **必须等所有监听器做完**才能继续（例如多个插件都要落盘）→ `parallel`
- 需要**可捕获的失败**→ `parallel`（`AggregateError`）

</details>

---

**本章一句话总结**：

> **服务**是「我知道我要什么」；**事件**是「我不知道有谁会关心」。五种分发模式决定了监听器能否**返回值**、能否**并发**、能否**短路** —— 而选择哪种模式，是**事件的约定**，不是监听器的自由。
