## 1.1 最小的插件 = 一个函数

**理论**：插件的全部契约，就是导出 `apply`，接收一个 `ctx`，用它注册你的贡献。

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
```

| 行 | 作用 | 必需吗 |
|---|---|---|
| `import type { Context }` | 只为类型注解，运行时消失 | 不是（但推荐） |
| `export const name = 'hello'` | **显示名**，出现在诊断/日志里 | 不是 |
| `export function apply(ctx)` | **插件本体** | ✅ 是 |

> 🔗 回扣 `agent-default-model`：那个插件是第三种形态（`extends Service`）。本章只是最基础的**函数形态**。

### 🧪 验证实验：最小插件

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-first-plugin/hello.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
```

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-first-plugin/cordis.yml`

```yaml
- name: './hello.ts'
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/01-first-plugin
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
hello from my first plugin
```

退出码 `0`。

**结论**：一行 `console.log` 就是一个完整的插件。没有 `main()`，没有 `register()`，没有配置对象 —— **`apply` 就是全部**。

## 1.2 启动器只做三件事

**理论**：`vendor/cordis/bin.js` 全文只有 16 行，它做三件事：

```js
import { Context } from '@deepseek-ai/cordis'
import { pathToFileURL } from 'node:url'
import Loader from '@deepseek-ai/cordis-plugin-loader'

const ctx = new Context()                              // ① 建根上下文
ctx.baseUrl = pathToFileURL(process.cwd()).href + '/'  //    设基准路径
await ctx.plugin(Loader)                               // ② 挂 Loader
await ctx.loader.create({                              // ③ 让 Loader 读 YAML
  name: '@deepseek-ai/cordis-plugin-include',
  config: { path: './cordis.yml' },
})
```

### ⭐ 第 ② 步：Loader 自己就是一个插件

```js
await ctx.plugin(Loader)
```

这句话和 `agent-default-model` 被挂载的方式**完全一样**。没有「框架核心」这种东西 —— 负责加载插件的那个东西，也是被加载进来的。

对应 architecture.md 第 13 行：

> There is no privileged core to patch: you extend dsh by mounting a plugin beside the others.

**「没有特权核心」不是口号，是 `bin.js` 第 10 行字面写着的代码。**

### `ctx.baseUrl` 的作用

相对路径需要基准。`baseUrl` 就是它 —— 这里设成**当前工作目录**，所以必须在实验目录下运行，`./hello.ts` 才解析得到。

### 🧪 验证实验：换个目录跑，`baseUrl` 就失效

这个实验**分两步**，分别证明 `baseUrl` 管着两件事。

**第一步：`cordis.yml` 本身也靠 `baseUrl` 找**

**▶️ 运行（故意在错误的位置跑）**

```sh

```

**输出（截取关键行）**

```

退出码 `1`。

> ⚠️ **实测更新（2026-09-23）**：现在**不崩也不报错** —— 失败被 loader 吞成 `logger.error`，实测是**零输出 + 退出码 0**，而且启动期日志会丢。用 `node --import tsx ../_diag.ts` 才看得到 `[E] include Error: config file not found: ...cordis.yml` 和 `Include = FAILED`。详见 [实测校验](../../examples/cordis-tutorial/README.md)。

→ 它去找的是 **`tmp/cordis-tutorial/cordis.yml`**（= 当前工作目录），而那里没有这个文件。

**第二步：插件模块的路径也靠 `baseUrl` 找**

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-baseurl/cordis.yml`

```yaml
# 本目录【故意不放】 hello.ts
- name: './hello.ts'
```

**▶️ 运行**

```sh

```

**输出（截取关键行）**

```

       failed to import loader entry ... (./hello.ts): Cannot find module
       '...\tmp\cordis-tutorial\01-baseurl\hello.ts'
```

退出码 `1`。

> ⚠️ **实测更新（2026-09-23）**：现在实测是**零输出 + 退出码 0**；用 `node --import tsx ../_diag.ts` 才看得到 `[E] include Error [ERR_MODULE_NOT_FOUND]: Cannot find module '...01-baseurl\hello.ts'`。下面「相对路径不是相对脚本」的结论**依然成立**，变的只是报错方式。详见 [实测校验](../../examples/cordis-tutorial/README.md)。

→ `./hello.ts` 被解析成 **`01-baseurl/hello.ts`**（= 当前工作目录），而不是 `01-first-plugin/hello.ts`。

**结论**：同样的 `bin.js`、同样的 `cordis.yml` 内容，**换一个工作目录就找不到文件**。

这直接证明了 `ctx.baseUrl = pathToFileURL(process.cwd()).href + '/'` 在起作用 —— **相对路径不是相对脚本，而是相对你从哪儿敲的命令**。

> ⚠️ 顺便带出一个**报错层级的区分**：第一步的失败发生在 **`include` 插件读配置文件**时（`config file not found`），第二步才轮到 **loader entry 导入模块**（`failed to import loader entry`）。[第 5 章](05-配置.md)会再遇到同族的报错，那时这个区分很有用。

## 1.3 `cordis.yml` = 插件清单，不是脚本

**理论**：`cordis.yml` 是一份**声明式的插件清单**，不是一段有执行顺序的脚本。

```yaml
- name: './hello.ts'
```

| 字段 | 含义 |
|---|---|
| `name` | 模块标识符 —— 相对路径或 npm 包名 |
| `config` | 传给插件的配置（第 5 章） |
| `id` | 被 patch 定位用的标识 |

> 🔗 `packages/bundle/base/cordis.patch.yml` **就是一份更长的 `cordis.yml`**，只是多了一层可被上层 patch 的能力。

（本节的验证并入下一节 —— 「清单不是脚本」的最强证据就是**清单里的位置不影响加载顺序**。）

## 1.4 三种插件形态

**理论**：Cordis 认识三种插件形态。

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

// 形态 1：函数插件 ← 本章写的
export function apply(ctx: Context) {}

// 形态 2：对象插件 —— 一个带 apply 方法的对象
export default {
  name: 'obj-plugin',
  apply(ctx: Context) {},
}

// 形态 3：类插件（Service 子类）← agent-default-model 用的
export class MyService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'myTutorialService')
  }
}
```

**选择规则（教程原话）：在需要公开服务之前，一直用函数形态。**

| 形态 | 什么时候用 |
|---|---|
| 函数 | 只做「注册事件、挂载子插件、监听」这类事 |
| 对象 | 同上但想带名字 —— 很少见。**只有对象形态必须叫 `apply`** |
| 类 | **要往 `ctx` 上挂一个新服务**（`ctx.xxx`） |

> 🔗 `agent-default-model` 用类形态，是因为它要公开 `ctx.agentDefaultModel`。若它只监听设置变化、不暴露任何东西，就该写成函数。

### 🧪 验证实验：三种形态都能跑

### 🧪 反面验证实验：没有 `apply` 的普通对象不是插件

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-not-a-plugin/greet-object.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'

export default {
  greet(ctx: Context) {
    console.log('这行永远不会执行')
  },
}
```

**▶️ 运行**

```sh

## 1.5 ⭐ 核心：位置不决定顺序

**理论**（教程原话）：

> 各项会**并发启动**，因此它们在列表中的位置**不保证插件的加载先后**；顺序由**服务依赖（`inject`）**决定，而非文件中的位置。

### 源码证据

`vendor/loader/src/config/group.ts:71`：

```ts
const outcomes = await Promise.allSettled(config.map(options => this.create(options)))
//                 ↑ 是 allSettled + map，不是 for-await
```

`map` 把每一项**立刻**转成 Promise —— 所有插件同时启动。

若设计成按顺序加载，这里会是：

```ts
for (const options of config) {
  await this.create(options)   // ← 串行，一个等一个
}
```

### 那为什么看起来「有顺序」？

因为 **`inject` 在背后建立了真正的顺序**：

```
配置项 A（要 settings）   ─┐
配置项 B（提供 settings）  ─┴─▶ 同时启动

A 发现 settings 还没有
   → fiber 进入 PENDING 挂起，不执行

B 注册 settings 服务
   → Cordis notify() 遍历所有等待 settings 的 fiber
   → 唤醒 A 的 fiber → A 开始执行 ✅
```

**顺序不是「写」出来的，是「依赖」出来的。**

这就是架构笔记里那句「行的顺序不携带加载语义」的**原因**。

### 🧪 验证实验：把消费者写在提供方【前面】

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-order/a-consumer.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'
import type {} from './b-provider.ts'

export const name = 'a-consumer'
export const inject = ['hello']

export function apply(ctx: Context) {
  console.log(`A（消费者）执行了 —— ${ctx.hello.greet()}`)
}
```

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-order/b-provider.ts`

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    hello: HelloService
  }
}

export class HelloService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'hello')
  }

  greet() {
    return '你好'
  }
}

export default HelloService
```

**📄 文件** `01-learn-basics/examples/cordis-tutorial/01-order/cordis.yml`

```yaml
# 注意：消费者写在【前面】，提供方写在【后面】
# 但 A 依赖 hello 服务，所以实际执行顺序由依赖决定，不由位置决定
- name: './a-consumer.ts'
- name: './b-provider.ts'
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/01-order
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
A（消费者）执行了 —— 你好
```

**结论**：消费者排在**第一位**，却拿到了**最后一个**才注册的服务。

如果加载真的按清单顺序来，A 执行时 `hello` 必然不存在 —— 它会卡在 PENDING 里一声不吭。**它跑出来了，就证明顺序是依赖决定的。**

> ⭐ 更强的证据在 [3.4 实验：PENDING 是静默的](03-服务.md#34--实验pending-是静默的)：把提供方整个删掉，A 会**完全静默**（不报错、不输出、退出码 0）。两相对照，才能确认「A 没输出」≠「A 失败了」，而是「A 在等」。

## 1.6 两个故障实验：报错的动词不同

**理论**：Cordis 把插件的启动分成**两个阶段**，报错时的动词不同。

| 实验 | 操作 | 错误信息 | 结果 |
|---|---|---|---|
| A | `apply` 里 `throw` | `failed to **apply** loader entry (./boom.ts): apply exploded` | 退出码 1 |
| B | 路径写成 `./missing-file.ts` | `failed to **import** loader entry (./missing-file.ts): Cannot find module` | 退出码 1 |

> ⚠️ **实测更新（2026-09-23）**：两个动词（`import` / `apply`）和各自的错误文案**实测都对**，但**退出码现在是 0**（错误不再抛出，只进 `logger.error`）。看错误需用 `node --import tsx ../_diag.ts`。详见本节末尾的[实测更新](#实测更新崩溃发生在启动期还是运行期)。

### 为什么动词不同

`vendor/loader/src/config/entry.ts:277-289` 是**两个独立的 try/catch**：

```ts
private async _init() {
  let plugin: any
  try {
    plugin = this.loader.unwrapExports(await this.parent.tree.import(...))
  } catch (error) {
    throw updateError('import', this.options, error)   // ← 解析阶段
  }
  try {
    await this._start(plugin)
  } catch (error) {
    throw updateError('apply', this.options, error)    // ← 启动阶段
  }
}
```

Cordis 把「**找不到模块**」和「**模块自己炸了**」分成两个阶段。看错误信息第一个动词就能定位：

- `failed to **import**` → 路径/包名写错，或模块本身语法错误
- `failed to **apply**` → 模块找到了、开始执行了，但 `apply` 里抛了异常

### 🧪 验证实验 B：模块路径写错

```yaml

```sh

node --import tsx ../_diag.ts                       # 预期报错：用这个才看得到错误

```
Error: failed to apply loader entry ... (@deepseek-ai/cordis-plugin-include):
       failed to import loader entry ... (./missing-file.ts):
       Cannot find module '...\01-error-import\missing-file.ts'

> ⚠️ **实测更新（2026-09-23）**：现在实测是**零输出 + 退出码 0**；用 `node --import tsx ../_diag.ts` 能看到 `[E] include Error [ERR_MODULE_NOT_FOUND]: Cannot find module '...missing-file.ts'`。

**结论**：两个实验的错误链**外层完全一样**（都是 include 插件 `failed to apply`），**只有内层动词不同**：

```
failed to apply loader entry (@deepseek-ai/cordis-plugin-include)   ← 外层：include 插件本身
  └─ failed to import loader entry (./missing-file.ts)              ← 内层：模块没找到
  └─ failed to apply  loader entry (./boom.ts)                      ← 内层：apply 抛异常
```

**读错误链要从最内层的 `[cause]` 往外看** —— 最内层才是真正的原因。

> ⚠️ **踩坑提醒**：因为外层永远是 `failed to apply`，只看第一行动词会被误导。真正的判据是**带具体文件名的内层那一行**。

### 实测更新：崩溃发生在「启动期」还是「运行期」

> **这一节的前提在当前 harness 上已经不成立。** 原文（2026-09-22）写的是「启动期崩溃、退出码 1」，因为当时 `group.ts` 的 `update()` 会把单条失败重新抛出：
>
> ```ts
> const failures = outcomes
>   .filter((outcome): outcome is PromiseRejectedResult => outcome.status === 'rejected')
>   .map(outcome => outcome.reason)
> if (failures.length === 1) throw failures[0]     // ← 这段在当前源码里已经不存在
> ```
>
> **现在**（2026-09-23，harness `c36a83ff6b`）同一个 `update()` 是：
>
> ```ts
> await this.create(newMap[id]).catch((error) => { this.ctx.logger.error(error) })
> ```
>
> 于是 `bin.js:11` 的顶层 `await` **永远不 reject**（实际跑下来验证过）：

```js
await ctx.loader.create({ ... })    // ← 再也不会有 rejection 浮上来
```

| 时机 | 模块解析失败时 | 退出码 |
|---|---|---|
| **启动期**（`bin.js` 读 `cordis.yml`） | 失败记进 `logger.error`，不抛出 —— 而且**启动期日志会丢**（exporter 还没注册），所以一个字都看不见 | **0** |
| **运行期**（热重载读 `cordis.yml`） | 记 `logger.warn`，旧配置回滚，进程照常活着 | `0` |

> **怎么看启动期的失败**：换用本系列的[诊断启动器](../../examples/cordis-tutorial/README.md#怎么看到失败用-_diagts)（它先把日志出口装上，再读 `cordis.yml`）：
>
> ```sh
> node --import tsx ../_diag.ts
> ```
>
> 实测能拿到 `[E] boom Error: apply exploded` 和 `boom = FAILED` —— **错误文案与本文记录逐字一致**，只有退出码不同。
>
> 想恢复「失败就抛」的老行为，得改 `vendor/loader/src/config/group.ts`（改法见 [实测校验](../../examples/cordis-tutorial/README.md#备选恢复失败就抛)），但那是改上游源码。
>
> 运行期那一半在 [6.2 运行期改坏 `cordis.yml`](06-组合与-HMR.md#62-运行期改坏-cordisyml崩还是记日志) 实测。

## 1.7 本章小结

```
bin.js                        cordis.yml                  hello.ts
  │                              │                            │
  │ ① new Context()              │                            │
  │ ② ctx.plugin(Loader)         │                            │
  │ ③ loader.create(Include) ───▶│ 读取                        │
  │                              │ 逐项 import ──────────────▶│
  │                              │ 并发 apply(ctx)             │ 执行 apply
```

1. **插件是一个导出 `apply(ctx)` 的函数** —— 没有框架启动代码，插件只描述自己的贡献
2. **组合发生在 `cordis.yml`** —— 一份插件清单，而不是一段脚本
3. **清单里的位置不决定加载顺序** —— 并发启动，顺序由 `inject` 依赖决定

## 1.8 自测

**Q1**：`cordis.yml` 里 a 写在 b 前面，但 a 需要 settings、b 提供 settings，谁先执行？

<details>
<summary>参考答案</summary>

**b 先执行。**

两者**同时启动**（`group.ts:71` 的 `Promise.allSettled`），但 a 发现 `settings` 不存在，fiber 进入 **PENDING** 挂起；b 注册 `settings` 后触发 `notify()`，a 才被唤醒。

若 a 和 b **没有依赖关系**，谁先执行**不确定**。

**自己验证**：`01-order/` 就是这个问题的最小复现 —— 消费者写在前面，照样最后一个跑。

</details>

**Q2**：报错 `failed to apply loader entry (./mytool.ts): u is not a function`，问题在哪？

<details>
<summary>参考答案</summary>

**模块找到了并且开始执行了**，所以不是路径问题。

问题在 `mytool.ts` 的**导出内容**：Cordis 期望拿到插件（`apply` 函数 / 带 `apply` 的对象 / Service 子类），但拿到的不是可调用的东西。

典型成因：`export default { greet() {} }` —— 一个**没有 `apply` 方法的普通对象**。

**自己验证**：跑 `tmp/cordis-tutorial/01-not-a-plugin/`，你会看到同一类错误，而且信息更完整：

```
invalid plugin, expect function or object with an "apply" method, received object
```

（`u` 这种短变量名是生产构建压缩后的产物。）

</details>

> 📌 **注意**：`export default function` **不是**这条错误信息的成因 —— 它是一个**完全有效的函数插件**，会正常运行（`05-default-export/` 实测）。
>
> 但它有**另一个**更隐蔽的坑，见下面 Q4。

**Q4（第 5 章补充）**：下面这个插件能跑，但有什么问题？

```ts
export const name = 'my-plugin'
export const inject = ['greeter']
export const Config = Schema.object({ /* ... */ })

export default function myPlugin(ctx: Context) {
  console.log('跑起来了')
}
```

<details>
<summary>参考答案</summary>

**所有模块级导出全部失效**：`name`、`inject`、`Config` —— 一个都不生效。

原因见 [5.4 的 `unwrapExports`](05-配置.md#54--核心config-挂在哪指针规则)：

```ts
unwrapExports(exports) {
  exports = exports.default ?? exports     // ← 返回 default 导出
  ...
}
```

Cordis 拿到的是 **default 导出的那个函数**，然后从**它**身上读 `name` / `inject` / `Config` —— 而函数上没有这些属性。

**自己验证**：跑 `tmp/cordis-tutorial/05-default-export/`。

```
📄 default-fn.ts
    模块级 export const inject = ['greeter']
    但没有任何插件提供 greeter

▶️ 输出
    插件跑起来了（说明 inject 没有被尊重！）
```

对比 `03-service-consumer-only/`（同样的 inject，但用的是具名 `export function apply`）→ **完全静默**。

**最危险的是它不报错** —— 插件照常运行，只是依赖关系、配置校验、显示名**全部静默失效**。

**规则**：要么全用**命名导出**（`export function apply` + `export const inject` + …），要么全用**类形态**（`export default class extends Service` + `static Config` + `static inject`）。**不要混用 default 导出和模块级元数据。**

</details>

**Q3**：为什么说「没有特权核心」？从 `bin.js` 找证据。

<details>
<summary>参考答案</summary>

`bin.js` 第 10 行：

```js
await ctx.plugin(Loader)
```

**负责加载插件的 Loader 本身，也是通过 `ctx.plugin()` 挂载的插件**。它和其他插件走完全相同的路径，没有特殊待遇，同样可以卸载、可以被替换。

要扩展 dsh，只需**在旁边再挂一个插件**。

</details>
