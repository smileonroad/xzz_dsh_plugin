## 5.1 概览

**理论**（教程原话）：

> `cordis.yml` 中的每个 Cordis 配置项都可以携带 `config` 块，插件则声明一个 **schema**，在运行 `apply` 前**验证**该块。错误配置会导致加载失败，并给出准确的错误：**插件绝不会在配置不完整时启动**。

### 本章的逻辑线

```
你的插件声明 Config（一个 Standard Schema）              ← 5.2  它「双重身份」是怎么回事
        ↓
cordis.yml 里的 config 块
        ↓
框架调 resolveConfig：校验 → 填默认值 → 才交给 apply     ← 5.3  这段源码是全章的地基
        ↑
        但有个前提：框架得【读得到】你声明的那个 Config   ← 5.4  ⭐ 本章重点
                                                           读不到 = 静默不校验，什么都不填
        ↓
读到了但值非法 → ValidationError + fiber FAILED           ← 5.6（实测退出码不是 1）
        ↓
`!!js` 让 config 的值推迟到加载时才求值                  ← 5.7
```

**一句话**：这一章真正难的不是「怎么写 schema」，而是 **`Config` 声明必须落在框架看得见的地方**。

教程那句「**插件绝不会在配置不完整时启动**」有个隐藏前提 —— 框架得先**找得到**你的校验器。找不到时它不报错，只是**当作你不需要校验**，然后一切照原样放行。

> ⚠️ 这就是 5.4 占用全章最大篇幅的原因：**唯一的坑在这里，而且它不发声。**

## 5.2 `Config` 的双重身份

**理论**：

```ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'config-demo'

export interface Config {                    // ← ① 类型
  greeting: string
  targets: string[]
}

export const Config: Schema<Config> = Schema.object({   // ← ② 运行时校验器
  greeting: Schema.string().default('Hello'),
  targets: Schema.array(String).default(['world']),
})

export function apply(ctx: Context, config: Config) {
  for (const target of config.targets) {
    console.log(`${config.greeting}, ${target}!`)
  }
}
```

> 导出的 `Config` **既是 TypeScript 接口，也是同名的运行时 schema**：消费方获得**类型**，Cordis 获得**验证器**。

**同名共存的原因**：TypeScript 有**两个独立的名字空间** —— 类型空间（`interface`）和值空间（`const`）。

### ⚠️ 精化：`Config` 的「可调用」是无关特性

一个自然的误读是「两个身份 = schema 和 function」。**不完全对**：

| | 名字 | 存在于 | 作用 |
|---|---|---|---|
| **类型空间** | `interface Config` | **只在编译期**，运行时消失 | 给消费方类型提示 |
| **值空间** | `const Config` | 运行时 | 给 Cordis 的**验证器** |

### 🧪 验证实验：Schema 实例到底长什么样

**📄 文件** `01-learn-basics/examples/cordis-tutorial/05-schema-shape/schema-shape.ts`

```ts
import Schema from '@deepseek-ai/schemastery'

const s = Schema.object({
  greeting: Schema.string().default('Hello'),
  targets: Schema.array(String).default(['world']),
})

console.log('① Schema 实例的 typeof      :', typeof s)
console.log('   它是可调用的吗？          :', typeof s === 'function')

console.log('\n② 直接调用它（Schemastery 自己的接口）')
console.log('   s({})          →', JSON.stringify(s({})))

console.log('\n③ 通过 Standard Schema 接口（Cordis 实际走的路）')
console.log('   有 ~standard 属性吗？     :', '~standard' in (s as any))
const result = (s as any)['~standard'].validate({})
console.log('   validate({}) 的完整形状   :', JSON.stringify(result))
console.log('   → 取值要用 .value        :', JSON.stringify(result.value))

console.log('\n④ 校验失败时的形状')
console.log('   ', JSON.stringify((s as any)['~standard'].validate({ targets: 'oops' }).issues))
```

**▶️ 运行**

```sh

```

**输出**

```
① Schema 实例的 typeof      : function
   它是可调用的吗？          : true

② 直接调用它（Schemastery 自己的接口）
   s({})          → {"greeting":"Hello","targets":["world"]}

③ 通过 Standard Schema 接口（Cordis 实际走的路）
   有 ~standard 属性吗？     : true
   validate({}) 的完整形状   : {"value":{"greeting":"Hello","targets":["world"]}}
   → 取值要用 .value        : {"greeting":"Hello","targets":["world"]}

④ 校验失败时的形状
    [{"message":"$.targets expected array but got oops","path":["targets"]}]
```

**结论**（四条）：

| 观察 | 说明了什么 |
|---|---|
| ① `typeof s === 'function'` | Schemastery 实例**确实可调用** |
| ② `s({})` 直接调用能用 | 但那是 **Schemastery 自己的接口** |
| ③ `'~standard' in s` → `true`，且 `validate({})` 返回 `{value: ...}` | ⭐ **Cordis 走的是这条** |
| ③ **默认值在 `.validate()` 里就填好了** | `{value: {greeting: 'Hello', targets: ['world']}}` |
| ④ 失败时返回 `{issues: [...]}`，**不抛异常** | ⭐ 抛不抛由 `resolveConfig` 决定（见 [5.3](#53-源码resolveconfig)） |

源码印证（`schemastery/src/index.ts:239-242`）：

```ts
const Schema = function (options: Schema) {
  const schema = function (data: any, options = {}) {
    return Schema.resolve(data, schema, options)[0]   // ← 调用它 = 校验
  } as Schema
```

> ⭐ **但 Cordis 用的是 `['~standard'].validate()`，不是直接调用。**
>
> 所以「它是函数」这件事在本场景中**无关**。也解释了教程那句「导出**普通对象**当 `Config` 无法工作」——
> Cordis **接受任意 [Standard Schema](https://standardschema.dev/) 验证器**，而普通对象**没有 `~standard` 属性**。

## 5.3 源码：`resolveConfig`

**理论**：`vendor/cordis/src/fiber.ts:50-62`：

```ts
export function resolveConfig(runtime: Plugin.Runtime, config: any) {
  if (!runtime.Config) return config                            // ① 没声明 schema 就放行
  const result = runtime.Config['~standard'].validate(config)   // ② Standard Schema 接口
  if ('then' in result) {
    throw new TypeError('Async config validation is not supported')   // ③ 不支持异步
  }
  if (result.issues) {
    throw new ValidationError(result.issues)                    // ④ 有错就抛
  } else {
    return result.value                                         // ⑤ ⭐ 返回【校验后的值】
  }
}
```

| 行 | 要点 |
|---|---|
| ① | **没有 `Config` 就完全不校验**，`config` 原样传进插件 |
| ② | `'~standard'` 是 Standard Schema 的约定属性名 |
| ③ | 异步校验**不支持** |
| ⑤ | ⭐ **`apply` 拿到的是 `result.value`** —— 这是 `.default()` 得以填充的位置 |

> 所以 `apply` 里**永远不需要写** `config.greeting ?? 'Hello'`。

## 5.4 ⭐⭐ 核心：`Config` 挂在哪（指针规则）

### 机制：`unwrapExports` 决定了 Cordis 看哪个对象

**源码**（`vendor/loader/src/index.ts:192-199`）：

```ts
/** Normalize ESM/CJS/default export shapes before applying a plugin. */
unwrapExports(exports: any) {
  if (isNullable(exports)) return exports
  exports = exports.default ?? exports        // ← ⭐ default 优先
  if (!exports.__esModule) return exports
  return exports.default ?? exports
}
```

整个规则只有两步：

```
第 1 步：确定「插件对象」是谁
         指针 = 有 export default ? default : 整个模块

第 2 步：只从【指针指向的那一个对象】上读 Config / inject / name
```

> ⭐ **一个反直觉的结论**：`export const Config` 和 `static Config` **地位完全平等**。
> 不是「类级覆盖模块级」，而是**「模块级根本没被看见」**。

### 📌 完整规则表

| 你的写法 | 指针指向 | `Config` 写在哪 | 结果 |
|---|---|---|---|
| `export function apply` + `export const Config` | **模块** | `export const Config` | ✅ |
| `export default 类` + `export const Config` | **类** | ✗ 挂在模块上了 | ⚠️ 静默不校验 |
| `export default 类` + `static Config` | **类** | `static Config` | ✅ |
| `export default { Config, apply }` | **对象** | 对象字面量里 | ✅ |
| `export class X`（无 default） | 模块 | — | ❌ 连插件都不是 |

> 🔗 **同一规律也适用于 `inject` 和 `name`** —— 它们都是 `Plugin.Base` 上的字段，从**同一个指针对象**上读。

### 🔍 一眼判断法：文件里有没有 `export default`

这是最容易看走眼的地方 —— `export default` 经常写在**文件最底下**，而 `Config` 通常写在**上半部分**，中间隔着一整个类的实现。扫一眼 `Config` 附近是**看不见**它的。

```sh
grep -n "export default" 你的文件.ts
```

- **搜到** → 元数据必须挂在那个 default 导出上（类是 `static`，对象就写进字面量）
- **搜不到** → 元数据写成模块级 `export const`

### 那「没写 `Config`」呢？—— 静默放行，这是设计

`resolveConfig` 第一行就是 `if (!runtime.Config) return config`：**没声明 schema 就放行**。不是每个插件都需要配置。

**📄 文件** `01-learn-basics/examples/cordis-tutorial/05-config-none/no-config.ts` —— 一个完全没有 `Config` 的类插件，配 `config: { targets: 'not-an-array' }` 跑：

```sh
cd tmp/cordis-tutorial/05-config-none
node --import tsx ../../../vendor/cordis/bin.js
```

```
   [没有 Config] apply 收到的 config = {"targets":"not-an-array"}
```

退出码 `0`。**所以报错只有一个来源** —— Cordis **找到了**一个 schema **且值不合法**：

| 情况 | 结果 |
|---|---|
| 没写 `Config` | 静默放行 ✅ 设计如此 |
| 写了但**读不到**（挂错位置） | 静默放行 ⚠️ **这才是坑** |
| 写了且读到了，值合法 | 校验通过，填默认值 ✅ |
| 写了且读到了，值非法 | `ValidationError` + fiber 进 FAILED（退出码实测不是 1） ✅ |

> ⚠️ **前两行在外部表现上一模一样。** 你分不清 Cordis 是「认为你不需要校验」还是「没找到你的校验器」—— **这就是这个 bug 难查的根本原因。**
>
> 用错了**不会报错**，非法值原样进插件，**类型声明变成谎言**：
>
> ```ts
> apply(ctx: Context, config: Config) {
>   config.targets   // 类型说 string[]，运行时是字符串 'not-an-array'
>   for (const t of config.targets) { ... }   // 💥 会逐个字符遍历！
> }
> ```

### 📊 实战：仓库里到底怎么写的？

统计 `packages/**/src/*.ts`（1595 个文件）：

| 写法 | 文件数 |
|---|---|
| `export const Config`（**函数形态**） | **70** |
| `static Config`（**类形态**） | 46 |

**函数形态反而更多。** 教程的判据是：**「在需要公开服务之前，一直用函数形态。」**

写起来的代码量也差一半：

```ts
// 函数形态 —— 2 个东西
export function apply(ctx: Context, config: Config) { ... }
export const Config = z.object({ ... })

// 类形态 —— 4 个东西
export class Foo extends Service {
  static Config = z.object({ ... })
  constructor(ctx: Context) { super(ctx, 'foo') }
}
export default Foo
```

> ⚠️ **「类 + `static` 更保险」这个说法要翻过来看。**
>
> **类形态不是「避免出错」，它是「引入了一个函数形态根本不存在的新错误面」。**
>
> ```
> 函数形态
>   export function apply(...)     ← 指针停在模块上，没得选
>   export const Config            ← 一定读得到 ✅
>                                  ⭐ 没有「挂错位置」这个可能性
>
> 类形态
>   export const Config            ← 挂在模块上
>   export default 类              ← 指针拐走了
>                                  ⚠️ 多了一个可以挂错的地方
> ```
>
> **这个坑是 `export default` 带来的，而 `export default` 是类形态带来的。**
>
> 所以准确的说法是：`static Config` 是**类形态内部最安全的写法**，不是**整体上最安全的形态**。

### 🎯 该选哪种：一张决策表

| 你的插件 | 写法 |
|---|---|
| 只注册事件 / 工具 / 子插件 | **函数** + `export const Config` ← **默认选这个** |
| 要公开 `ctx.xxx` 服务 | **类** + `static Config` ← 一旦决定用类，这是唯一正确写法 |
| 类是必需的，但 schema 还要给别人复用 | 模块级定义 + `static Config = Config` |

**最后一行是真实存在的写法** —— 全仓库有 2 个文件同时写了两个，而且**不是 bug**：

**📄 文件** `packages/session/session-telemetry-otel/src/index.ts:129,158`

```ts
export const Config = z.object({ ... })          // 模块级定义

export class OpenTelemetrySessionBackend extends SessionTelemetryBackend {
  static Config = Config                         // ⭐ 只是【引用】上面那个
  ...
}
export default OpenTelemetrySessionBackend
```

| 位置 | 作用 |
|---|---|
| `export const Config` | 供**其他模块 import 复用**（工具、测试、类型推导） |
| `static Config = Config` | 让 **Cordis 读得到** |

`static Config` 在这里只是个**指针**，schema 本体还在模块级 —— **两个诉求都满足了**。

## 5.5 ⭐ 统一图景：`Plugin.Base`

**理论**：`vendor/cordis/src/registry.ts:100-108`：

```ts
export interface Base<T = any> {

  name?: string                                     // ← 第 1 章：export const name
  /** Standard-schema validator applied to config before the plugin starts. */
  Config?: StandardSchemaV1<any, T>                 // ← 第 5 章：export const Config / static Config

  inject?: Inject                                   // ← 第 3 章：export const inject
```

### `ValidationError` 源码（`fiber.ts:19-35`）

```ts

      } else {
        return `  - ${issue.message}`
      }
    }).join('\n'))

}
```

> 🔗 **对上了**：这段代码里的 `  - ${issue.message} (at ${issue.path.join('.')})` 就是输出里那行

> ```
>
> 而 `issue.message` / `issue.path` 的**来源**就是 5.2 实验④里看到的 `[{"message":"...","path":["targets"]}]` —— **Schemastery 产出 issues，Cordis 只负责格式化**。

### ⚠️ 校验的边界

教程第 68 行：

> 如果某个插件的配置**通过了 schema 验证**，但其中指定的**资源或提供方不可用**，该插件也应当在能解析该引用时**立即拒绝**。

**schema 只保证「形状」，不保证「引用可用」。** 例如 `provider: 'deepseek-official'` 通过了 `z.string()`，但这个 provider 是否真的注册了，schema 管不了 —— 得由插件自己在 `apply` 里检查。

## 5.7 `!!js`：加载时求值

**理论**：YAML 里的 `!!js` 标签让一个标量在**加载时**被当成 JS 表达式求值。

### 🧪 基本用法：把环境变量读进 `config`

**📄 文件** `01-learn-basics/examples/cordis-tutorial/05-js-tag/cordis.yml`

```yaml
# !!js 标签：这个字符串会被当成 JS 表达式求值（能读到 process.env）
- name: './js-tag-demo.ts'
  config:
    greeting: !!js process.env.DEMO_GREETING
    target: env-test
```

（`js-tag-demo.ts` 是个普通插件，`Config` 里 `greeting` 默认 `'Hello'`，`apply` 里打印 `${greeting}, ${target}!`。）

**▶️ 运行**（两次：设了环境变量 / 没设）

```sh
cd tmp/cordis-tutorial/05-js-tag
DEMO_GREETING="你好" node --import tsx ../../../vendor/cordis/bin.js   # → 你好, env-test!
node --import tsx ../../../vendor/cordis/bin.js                       # → Hello, env-test!
```

**输出**

```
你好, env-test!
Hello, env-test!
```

**结论**：环境变量**进了 `config`**。第二次因为 `process.env.DEMO_GREETING` 求值成 `undefined`，**`.default('Hello')` 把它补上了**。

> ⭐ 两次运行合起来说明：**`!!js` 的求值发生在 schema 校验之前**。表达式结果先进入 `config`，再被 `resolveConfig` 校验/填默认值。
>
> 所以 `!!js` 结果非法时（比如求值成 `123` 而 schema 要 string），报错的是 **`ValidationError`**，不是 `!!js`。

### ⚠️ 只有 `config` 和 `disabled` 会求值

**别处的 `!!js` 不报错、也不求值** —— 它只是一个普通的 `{__jsExpr: "..."}` 对象，原样躺着。

**📄 文件** `01-learn-basics/examples/cordis-tutorial/05-js-tag-id/cordis.yml`

```yaml
- name: './js-tag-demo.ts'
  id: !!js process.env.DEMO_GREETING
```

**📄 文件** `01-learn-basics/examples/cordis-tutorial/05-js-tag-id/probe.ts`（一个自定义启动器，用来窥视 entry 的原始 options）

```ts
import { Context } from '@deepseek-ai/cordis'
import Loader from '@deepseek-ai/cordis-plugin-loader'
import { pathToFileURL } from 'node:url'

const ctx = new Context()
ctx.baseUrl = pathToFileURL(process.cwd()).href + '/'
await ctx.plugin(Loader)

// entry-init 在 Entry 构造函数里、options 赋值之前就发出了，
// 所以这里只记下引用，等加载完再回头看。
const seen: any[] = []
ctx.on('loader/entry-init', (entry: any) => seen.push(entry))

await ctx.loader.create({
  name: '@deepseek-ai/cordis-plugin-include',
  config: { path: './cordis.yml' },
})

for (const entry of seen) {
  console.log('name           =', entry.options?.name)
  console.log('  options.id   =', JSON.stringify(entry.options?.id))
```

**▶️ 运行**


**输出**

```

  options.id = "e4fbdd38"
  typeof id  = string
  生效的 id  = e4fbdd38
name         = ./js-tag-demo.ts
  options.id = {"__jsExpr":"process.env.DEMO_GREETING"}
  typeof id  = object
  生效的 id  = e4fbdd38:[object Object]
```

（`e4fbdd38` 这类短哈希是**每次运行现生成的** —— 再跑一次会变成别的值。变的是哈希，**`[object Object]` 不变**。）

| 观察 | 说明 |
|---|---|
| **退出码 0**，插件正常运行 | ⚠️ **没有任何报错** |
| `options.id` 是 **`{"__jsExpr":"process.env.DEMO_GREETING"}`** | `!!js` **没有被求值**，原样躺着 |
| `typeof id` 是 **`object`**，不是 `string` | 参数类型已经错了 |
| 生效的 id 变成 **`e4fbdd38:[object Object]`** | ⭐ **静默产生了一个垃圾 id** |

**为什么** —— 求值函数 `interpolate`（`vendor/loader/src/config/utils.ts`）在整个 loader 里**只有一处调用**：

```ts
ctx.on('internal/config', function (this: Fiber, _config, next) {
  const config = next()
  ...
  return interpolate(this.ctx, config)       // ← 只处理 config
}, { global: true })
```

`disabled` 是另一条独立路径（`entry.ts:104-107` 的 `disabledOf`，调 `this.evaluate(...)`）。

### 📌 作用范围

| 字段 | `!!js` 可用？ | 用错时会怎样 |
|---|---|---|
| `config` | ✅ 会求值 | — |
| `disabled` | ✅ 会求值 | — |
| `name` / `id` / `inject` 等元数据 | ❌ **不求值** | ⚠️ **不报错**，原样留着 `{__jsExpr}` 对象（`id` 会变成 `[object Object]`） |

> ⚠️ **这是最危险的一类坑**：报错至少会让你发现写错了；**静默产生 `[object Object]` 则完全无声**。
>
> 这正是 5.4 那个规律的**又一个实例** —— **挂错位置不报错，只静默失效**。
>
> 也是 [第 2 章 Q3](02-生命周期与-effect.md#28-自测)那条注脚的印证：**「宁可炸不可静默」是 Cordis 的倾向，不是保证。**

### `disabled: !!js` 的用途：按环境门控

> 可以按**平台或环境**门控一行 —— 例如只在 macOS 上挂载某个插件。

源码依据（`entry.ts:104-107`）：

```ts
private disabledOf(options: EntryOptions): boolean {
  return isJsExpr(options.disabled)
    ? Boolean(this.evaluate(options.disabled.__jsExpr))    // ← 每次决策时求值
    : Boolean(options.disabled)
}
```

`validate` 那一处（`include/src/index.ts:262`）：


**📄 文件** `01-learn-basics/examples/cordis-tutorial/05-config-not-array/cordis.yml`


## 5.8 自测

**Q1**：我写了个类插件，加了 `export const Config`，但非法配置没有被拦截。为什么？

<details>
<summary>参考答案</summary>

因为你的模块有 `export default` 导出。

`unwrapExports` 返回 **default 导出**（那个类），Cordis 从**它**身上读 `.Config` —— 而 `.Config` 在**模块命名空间**上，不在这个类上。

**修法**：改成静态属性

```ts
export class MyPlugin extends Service {
  static Config = Schema.object({ ... })     // ✅
  ...
}
export default MyPlugin
```

**自己验证**：并排跑这两个目录，看输出的差异 ——

```sh
cd tmp/cordis-tutorial/05-config-class-module && node --import tsx ../../../vendor/cordis/bin.js
cd ../05-config-class-static                   && node --import tsx ../../../vendor/cordis/bin.js
```

**更狠的一刀**：再跑 `05-config-class-module-default/`，你会看到 `config` 连 `undefined` 都算不上的东西 —— **`config` 就是 `undefined`**。

> ⚠️ 这个错误**不会报任何警告** —— 配置只是静默地不被校验。类型声明仍然有效（编译期），所以你会以为一切正常，直到运行时拿到形状错误的值。

</details>

**Q2**：`.default()` 填充的值，是在哪一步进入插件的？

<details>
<summary>参考答案</summary>

在 `resolveConfig` 的**最后一行**：

```ts
return result.value      // ← 校验后的值
```

流程：

```
cordis.yml 的 config 块
    ↓
resolveConfig(runtime, config)
    ↓  runtime.Config['~standard'].validate(config)
    ↓  → { value: { greeting: 'Hello', targets: [...] }, issues: undefined }
    ↓
return result.value          ← .default() 在这里已经填充完毕
    ↓
apply(ctx, config)           ← 拿到的一定是完整对象
```

**自己验证**：`05-schema-shape/` 的实验③ 直接打印了 `validate({})` 的返回值 —— 你会看到默认值**在那一步就已经在里面了**。

**所以 `apply` 里永远不需要写 `config.greeting ?? 'Hello'`** —— schema 已经保证了。

</details>

**Q3**：schema 校验通过了，插件就安全了吗？

<details>
<summary>参考答案</summary>

**不。** schema 只保证**形状**，不保证**引用可用**。

```ts
export const Config = Schema.object({
  provider: Schema.string().required(),     // 'openai' 能通过校验
  model: Schema.string().required(),        // 'gpt-9' 也能通过校验
})
```

但如果 `openai` 这个 provider 根本没注册、`gpt-9` 这个模型不存在 —— **schema 一无所知**。

教程第 68 行的要求：

> 如果某个插件的配置通过了 schema 验证，但其中指定的**资源或提供方不可用**，该插件也应当在**能解析该引用时立即拒绝**。

即：

```ts
export function apply(ctx: Context, config: Config) {
  const provider = ctx.llm.providers[config.provider]
  if (!provider) throw new Error(`unknown provider: ${config.provider}`)   // ← 自己检查
  ...
}
```

**这就是 [第 1 章](01-第一个插件.md)那条原则的又一次应用** —— 宁可立刻抛出，不可静默降级。

</details>

**Q4**：`!!js` 写在 `id` 字段上会发生什么？

<details>
<summary>参考答案</summary>

**什么都不会发生 —— 除了一个静默变形的 id。**

`!!js` **只在 `config` 和 `disabled` 两个字段被求值**（`interpolate` 只作用于 config；`disabledOf` 单独处理 disabled）。

写在别处 → **不报错、不求值** → 那个字段的值就是一个普通的 `{__jsExpr: "..."}` 对象。

实测（`05-js-tag-id/`）：

```
options.id   = {"__jsExpr":"process.env.DEMO_GREETING"}
typeof id    = object
生效的 id    = e4fbdd38:[object Object]
```

**退出码 0**，插件照常运行，只是 id 变成了垃圾字符串。

**自己验证**：

```sh
cd tmp/cordis-tutorial/05-js-tag-id && node --import tsx probe.ts
```

> ⚠️ 这是「挂错位置静默失效」规律的第三个实例（前两个是 5.4 的 `Config` 和 `inject`）。**Cordis 在这类问题上不报错。**

</details>

---

**本章一句话总结**：

> `Config` 是**同一个名字的两种身份** —— 给 TypeScript 的类型，和给 Cordis 的验证器；而它**挂在哪里**（模块级导出 vs `static`）取决于你的插件是**函数形态**还是**类形态**，挂错了会**静默失效**。
