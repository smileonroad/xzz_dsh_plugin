# 2026-09-17 — scripted-llm-adapter，给 harness 接一个不用联网的模型

## 事情是这样的

前面十来篇，命令、工具、能力 seam、事件、审批、界面都摸过一遍了。units-capability 那篇自造了一条能力 seam，练的是怎么设计一条；events-demo 那篇练的是瀑布事件里观察者和决策者的纪律。这些插件挂的位置各不相同，但底下压着同一条地基，模型那一轮调用。工具要等模型决定调它，事件里的内容多半是模型写出来的，界面渲染的也是模型的产物。这条地基一直没有亲手搭过。

起因还很具体。我本来只想办一件小事，输入里出现「权限」这类词的时候别让模型看见，直接回一句让用户重新输入。真动手才发现这件事牵出一个更基础的问题。在 harness 里，「模型」不是一个函数调用，而是一份相当较真的协议，你没弄懂它就没法稳妥地改它的行为。

所以这一篇自己当了一次模型提供方。写出来的东西叫 `scripted-llm-adapter`，一个不联网、不要密钥、说什么全由规则决定的模型。它能在 headless 里一条命令跑起来，也能出现在 web 的模型选择器里。顺带那个敏感词门禁也做了，挂在模型调用之前。

这个实战的开发过程本身也是一课。线协议契约变过、配置分层压过我的配置、patch 里的路径锚点跟我以为的不一样，三处都让我改了不止一次。坑都收在倒数第二节。

## 模型调用这一路经过谁

先把链条画出来，后面所有讨论都落在这张图上。

```
agent loop 决定要问模型
      │  组装请求（历史消息、系统提示词、工具 schema、生成参数、取消信号）
      ▼
 ctx.llm.stream(请求)
      │  ① llm/stream 瀑布，插件可以在这里包一层，也可以根本不往下传
      ▼
 选路由，请求里的 provider 决定找哪个适配器，model 是厂商那边的模型 id
      │  ② prepareCall 先问能力，再绑定这一代适配器的 stream 入口
      ▼
 adapter.stream(请求)        ← 这一篇实现的就这个方法
      │  ③ 产出规范分片
      ▼
 装配器把分片拼成一条完整的助手消息
      │
      ├─ 模型要求调工具，工具执行，结果塞回历史，再来一轮
      └─ 不然这一轮就结束了，消息进会话
```

`packages/llm/llm/src/index.ts` 里的 `LlmAdapter` 是个抽象类，四个方法只有 `stream()` 必须自己写。另外三个都有默认实现，`providerInfo` 报身份，`listModels` 报目录，`resolveModel` 报能力。`prepareCall` 的默认实现做一件值得留意的事，它把「问到的能力」和「这一次要用的 stream 入口」绑成一个原子对。原因是给动态目录型的适配器留后路，防止两次查询之间配置换了，出现拿 A 代的能力去发 B 代的请求。

这一步还解释了一件小事。适配器的 `resolveModel` 声明了哪些 reasoning 强度，就真的会被拿去校验。调用方显式点名一个没声明的强度，服务在调用 `stream()` **之前**就拒绝，测试里我用「适配器一次都没被调到」来钉死这条。

## 分片这件事比想象中较真

模型回话不是一句话，是一串分片。七种分片归起来只有三件事，三种内容块（文本、思考、工具调用）、每个块的开始与结束、以及收尾的用量和结束原因。块之间靠 `index` 关联，同一块的每次增量复用同一个编号，最后由 `block-end` 一次性交出拼好的整块。

义务有几条，`packages/llm/llm/src/types.ts` 的注释写得很清楚。每个 `block-start` 必须有配对的 `block-end`，`usage` 要在 `finish` 之前，`finish` 之后不许再冒任何东西，工具调用的参数从头到尾都是原始 JSON 字符串，增量用 `argumentsDelta` 送。

真正让我记住这些的不是注释，是 `packages/llm/llm/src/invariant.ts`。它自己就是一个 `llm/stream` 的监听器，注册时带 `{ global: true, prepend: true }`，排在所有插件前面，逐块检查上面那几条。也就是说，文档上的承诺可以变成一条会失败的测试。我特意写了个坏适配器，在 `finish` 之后又发了一个 `text-delta`，整条流当场以 `LLM stream emitted text-delta after terminal finish` 结束。

一条工具调用的分片长这样，抄自测试里的断言。参数被刻意拆成两段增量，让「拼」这个动作看得见。

```
block-start      index 0  tool-call
tool-call-delta  index 0  id 名字 argumentsDelta '{"text":'
tool-call-delta  index 0  id 名字 argumentsDelta '"hi"}'
block-end        index 0  块 = { 原始 JSON 字符串 }
usage
finish           reason tool-calls
```

这一招我后来当成了习惯。约束能被故意违反一次并当场抓到，比读三遍文档都牢。

## 离线模型怎么说话

既然不做真实推理，就得有一套能复现的规则。规则很短，最后一条人类消息的开头决定这一轮说什么。

```
think:<内容>                 先说思考块再说文本块
tool:<名字> <JSON>           要求调工具
fail:<CODE> <描述>           适配器抛错
provider-fail:<CODE> <描述>  以 error finish 收流
empty:                      正常结束但无内容，按 EMPTY_RESPONSE 报错
hang:                       发半截文本后停住等取消
其它                          回显 [scripted] 原文
```

这套前缀让演示和测试共用一条通道，也让上面那些协议细节都能被手动触发。挑 `think:` 是为了练多块的编号分配，挑 `tool:` 是为了跑通两轮回路，剩下四条各自对应一条错误或取消路径。

## 目录与选择，都是建议性的

模型提供方还要回答两个问题，你有哪些模型，某个模型的准确能力是什么。这两件事在 harness 里分得很开。

`listModels` 是目录，只用来展示。目录里没列出的模型 id 照样能用，测试里专门断言了这一点，一个不在目录里的 id 返回的身份就是它自己，没有任何伪造的能力声明。准确能力放在 `resolveModel`，那里才有上下文窗口和 reasoning 选项。

浏览器里的模型选择器读的是另一个函数，`packages/api/session-controller/src/catalog.ts` 的 `buildModelCatalog`。它把每个提供方的目录、能力、失败分组拼成一个结构交给界面。我原先在 README 里写着「选择器能不能看到还没验证」，后来补了一条测试直接调这个函数，断言 `Scripted (scripted)` 这个分组和 `Scripted demo` 都在里面。顺带一个意外收获，测试里我一开始把导入路径写成了包的内部文件，跑不通，才注意到这个包只导出根入口，examples 里想用深路径得从根入口拿。

## 出错有两条路，消费方只看到一条

适配器遇到故障，可以抛一个带稳定 code 的 `LlmError`，也可以以 `finish { kind: 'error' }` 或者 `{ kind: 'aborted' }` 收流。前者是传输和协议故障，后者是提供方自己带内的故障。两条路的差别只在适配器这一侧。

消费方看到的只有一条路。`LlmRuntime.stream()` 会把抛出来的异常**规范化**成终态 finish 再交出去，所以用户侧永远拿到一条结束分片，不会拿到异常。这是最容易记反的一点，我第一版断言写成了「抛出去」，跑起来才发现拿到的是 `finish`，只好改成断言 `finish.reason.failure.code`。

取消也一样。规则里有一条 `hang:`，发半截文本就停住不动，等信号。中途取消的时候适配器抛错，运行时按信号把它归类成 `aborted`。测试里我先等第一个分片真的落地再取消，否则取消会早于任何内容，会话里连一条打断的助手消息都不会留下，这个细节第一次就写错了。

## 离线模型踩到的三处反直觉

三处都跟「怎么从请求里认出用户那句话」有关，代码里各留了一处判断，测试各有一条用例。

| 现象 | 处理 | 原因 |
| --- | --- | --- |
| 工具结果消息的 `role` 是 `user` | 不看角色，看有没有 `tool-result` 块 | 规范词汇里工具结果复用 user 角色，只看角色会把它当成新的用户指令 |
| harness 会往历史里插它自己生成的 user 消息 | 优先取 `source.kind === 'user'` 的那条 | 工作区指令、技能目录这类内容也以 user 消息进入请求，但它们不是人说的话 |
| 会话日志里存的不是适配器原样的分片 | 断言改成打包形态 | 连续增量会被折成一条 `text-chunks` 记录，为了重放时无损又省地方 |

第一条的后果最直接。工具结果被当成新指令，模型就会再调一次同一个工具，然后又一次，直到你发现不对。我第一版就是这么写的，测试里两个回合直接变成了无限回合。

第二条是演示帮我抓到的。第一次跑 headless，屏幕上的回复是 `[scripted]` 加上一整篇技能目录，因为最后一条人类文本被 harness 注入的提醒顶掉了。用人话说，模型不能靠「最后一条 user 消息」认人，得像人一样分辨谁在说话。

## 顺手做的拦截层

回到开头那件小事。命中敏感词就不让模型看见，直接回一句重新输入。

这件事没有写进适配器，位置不对。策略不该长在提供方身上，你把离线模型换成真的 deepseek，适配器就换了，门禁也跟着没了。它属于「模型调用之前」，而图上第 ① 步那条瀑布正好就是这个位置。

`src/guard.ts` 挂上 `llm/stream`，命中词表时自己造一段合规分片当回答，适配器一次都不会被调用。三个细节值得记。

判断对象必须是**人说的话**，工具结果和注入的提醒都不算，这条直接复用离线模型里那个 `lastUserText()`。

`options.purpose` 非空的是压缩、起标题这类后台调用，必须原样放行，否则会把它们一起打断。

拒绝时返回的流也得**合规**，因为它和适配器的产出走同一条校验。这条我没放过，测试里把门禁挂在包不变量下面又跑了一遍，确认拒绝流本身不会被拦。

| 想做的事 | 用哪个扩展点 | 代价 |
| --- | --- | --- |
| 命中就回一句自定义文案，不调模型 | `llm/stream` 瀑布 | 回复得是一段合规分片流，用户原文仍会进会话 |
| 静默吞掉这一步 | `agent/pre-step` 返回 `{ kind: 'reject' }` | 这一轮以 blocked 结束，同样拦不住原文产生 inbox 事件 |
| 脱敏或补上下文后放行 | `agent/pre-step` 返回 `{ kind: 'enter', messages }` | 模型还是会被调用，只是看到的是改写后的内容 |

这里有个我没堵上的缺口。门禁只挡住了模型，用户的原文已经进了会话历史。如果合规上要求命中的原文根本不落盘，得换第三种里的 reject 路线，并且自己核一遍认领事件里还带不带原文。README 的已知限制里如实写了这条。

## 测试是怎么写的

二十一条，分五组。规矩还是老一套，描述现在是这样工作的，装配真实服务走真实边界。

端到端那几条用 harness 自己的测试装配 `agent-loop-testkit`，挂上真实的 `AgentLoop`，把插件当普通插件装进去，然后像用户一样发消息。看的是模型说的话有没有拼成一条助手消息，用量算得对不对，工具能不能真的被调起来。这里有个取舍值得说，我一开始想全用手工装配，后来发现 testkit 的 README 本身就说「测试仍然负责适配器」，正好把这次被测的东西留在了外面，装配反而更干净。

协议那几条只挂 `LlmRuntime`，直接读 `ctx.llm.stream()` 的输出。不经过 agent，一层干扰都没有，断言也短。故意写错的流、抛错规范化、带内故障、`UNSUPPORTED_OPTION`、`EMPTY_RESPONSE`、中途取消都在这一组。

剩下三组分别管能力声明、注册语义、拦截层。注册那组值得一提，它把平时不会遇到但一旦遇到就难查的规矩都钉住了，同一个路由不能有两个适配器，`replace()` 换路由是原子的，句柄释放之后再换会抛 `REGISTRATION_DISPOSED`。

写测试的时候有两条心得。凡是「框架保证 X」的说法，都值得配一条会让它失败的用例。`finish` 之后不许发分片是这样，没声明的 reasoning 强度不许调用 `stream()` 也是这样，后者我用的证据是适配器记录的请求数为零。

```ts
const failure = await ctx.llm
  .prepareCall({ provider: 'scripted', model: 'demo', reasoningEffort: ReasoningEffortId('extreme') })
  .then(() => undefined, (error: unknown) => error as { code?: string })
expect(failure?.code).toBe('UNSUPPORTED_REASONING_EFFORT')
expect(adapter.requests).toHaveLength(0)   // 连 stream 都没进来
```

拦截层那组的核心也在这条线上。命中的时候不能只说「返回了拒绝文本」，还要证明适配器**一次都没被调到**，否则说不定模型已经跑完了，只是回复被换掉了。

## 工程上还有三处现实的坑

**线协议会变，产物得跟着重生成。** reply-tips 那个双端包在我提交前突然启动失败，报的是参数编码器没有 `create()` 工厂。翻 harness 的提交记录才发现，当天上游把边界编码器从「直接给 schema」改成了「给一个首次使用时才物化的 create 工厂」。我的线协议产物是几天前生成的，字段还是旧名字，新加载器一律拒收。结论很朴素，跨仓库的生成物没有版本约束，上游一动就得重跑生成脚本。

**配置分层会压过你的配置。** 我给 patch 里写了默认模型指向离线提供方，跑起来回答我的却是真模型。原因是 `~/.dsh/settings.yaml` 里早就存了用户的模型选择，settings 是叠在组合配置之上的用户层，优先级更高。csv-query-tool 那篇讲过的配置分层，这次从另一个方向又咬了我一口。这也解释了为什么离线演示要自带一个一次性 `DSH_HOME`，把 settings 和 overlay 都放进临时目录，跑完删掉，谁的真实环境都不动。

**patch 里的路径锚点跟我以为的不一样。** 仓库文档一直写的是「相对 profile 目录解析」，我就照着写 `./examples/<项目>/src/index.ts`，启动报的却是 `<项目目录>/examples/<项目>/src/index.ts`。实测下来锚点是**声明这一行的 patch 文件所在目录**。只有放在 profile 目录里那份 `cordis.patch.yml` 才按 profile 目录解析，那份才需要 examples junction。这一个坑我顺手把仓库里九个 patch 和六组 README 全改了过来，文档不改的话，下一个会话还会踩。

## 接下来该干嘛

这个模型提供方是进程内的，不解析任何厂商协议。往上一层可以把它换成真的 wire 适配器，对着 `packages/test-support/llm-mock-server` 那个 OpenAI 兼容的故障服务器写 HTTP 与 SSE，把请求映射、`attributionHeaders()`、重试分类都练一遍。`llm/stream` 这条瀑布也才用了一小半，超时、脱敏、用量计量都还没做过。

另一条路是继续往上游走，去看提示词那一层。`ctx.systemPrompt` 是另一条带提供方角色的 seam，管的是系统提示词怎么拼起来，跟模型边界正好是同一件事的两端。往那边走之前，先把这篇的坑记住一条就够用了。分片契约不是文档承诺，是有代码在查的。
