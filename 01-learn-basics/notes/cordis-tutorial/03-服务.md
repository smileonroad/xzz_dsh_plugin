## 3.1 服务是什么

**理论**：**服务**是一个插件**提供**、其他插件通过 `ctx` **消费**的具名能力。

harness 里全是服务：`ctx.tools`、`ctx.llm`、`ctx.agents`、`ctx.sessions`。

**关键设计**（教程第 5 行）：

> 消费方**只指定** `'tools'` 之类的能力，**而不导入其提供方**，因此配置可以选择提供方，**无需修改消费方**。

这就是「能力缝」（capability seam）在代码层面的形态 —— 也是为什么 architecture.md 说「一次提供方替换就能改变整个产品」。

## 3.2 提供服务的两部分：运行期 + 编译期

**理论**：提供服务要写**两件**互不相干的事。

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

// ── 编译期：声明合并 ──
declare module '@deepseek-ai/cordis' {
  interface Context {
    greeter: GreeterService
  }
}

// ── 运行期：注册 ──
export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')
  }

  greet(who: string) {
    return `Hello, ${who}!`
  }
}
```

| 部分 | 作用 | 生成代码？ |
|---|---|---|
| `super(ctx, 'greeter')` | **运行期**注册实例，此后任何插件都能 `ctx.greeter` | ✅ 有 |
| `declare module { ... }` | **编译期**让 `ctx.greeter` 通过类型检查 | ❌ **无** |

教程原话：

> 没有该声明时，服务在**运行时仍能工作**，但消费方会**失去类型安全**。

> 🔗 **回扣 TS 笔记**：`declare module` 就是 TypeScript 的 **declaration merging**。这也正是 `agent-default-model` 里那段 `declare module` 的作用 —— 让 `ctx.agentDefaultModel` 有类型。
>
> 也解释了本项目「双 face」（host/client 分开编译）的根因：两侧往同一个 `Context` 接口合并**同名不同实现**的属性，放一个 program 里会冲突。

## 3.3 ⭐ 消费服务的三种写法（完整图景）

**理论**：

```ts
// ① 硬依赖
export const inject = ['greeter']
export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))   // ← 保证已就绪
}
```

```ts
// ② 可选依赖：使用处探测
export function apply(ctx: Context) {
  const greeter = ctx.get('greeter')        // ← 可能是 undefined
  console.log(greeter?.greet('maybe') ?? 'no greeter available')
}
```

```ts
// ③ 可选 + 响应式（你之前学的 settings 用的就是这种）
ctx.inject(['greeter'], (greeterCtx) => {
  // 服务就绪时才跑；晚到也能唤醒
})
```

| 写法 | 语义 | 服务缺失时 | 服务**后到**时 |
|---|---|---|---|
| ① `export const inject = [...]` | **硬依赖** | 整个插件 PENDING，不加载 | 自动加载 |
| ② `ctx.get('name')` | **可选，一次性探测** | 照常加载，拿到 undefined | ❌ **永远错过** |
| ③ `ctx.inject([...], cb)` | **可选，响应式** | 主插件照常，分店 PENDING | ✅ **分店自动开门** |

> **这张表就是 `agent-default-model` 选 ③ 的完整理由** —— 之前只讲了 ① vs ③，现在补齐 ②。

### 🔬 深挖：`export const inject = [...]` 这句声明**到底做了什么**

这是被问得最多的一句。它**不是 import**，什么也没取回来。它做的是三件事：

| # | 作用 | 不写会怎样 |
|---|---|---|
| **1** | **时序门控** —— 依赖到齐前**不调用 `apply`** | `apply` 立刻跑，服务可能还不存在 |
| **2** | **把服务解析进本 fiber 的 `store`** —— 这才是 `ctx.greeter` 能被找到的原因 | 查找链走到头，抛错 |
| **3** | **依赖变化时自动重载** —— 提供方走了就卸载，回来就重新 `apply` | 你拿到的是过期的引用 |

**📄 文件** `01-learn-basics/examples/cordis-tutorial/06-inject-why/`

**逐条读**：

| 观察 | 对应哪个作用 |
|---|---|
| t=0 时 `parent` / `late` **一个字都没打印** | **作用 1**：依赖没到齐，`apply` 根本不调用 |

#### 机制零：`inject` 的第一跳 —— 填充 `_store`

`vendor/cordis/src/fiber.ts:314-319`（fiber 初始化时）

```ts
if (this.uid !== null && parent.fiber.state !== FiberState.UNLOADING) {
  for (const name of Object.keys(this.inject)) {
    this._checkImpl(name)          // ⭐ 逐个人 inject 的名字去找实现
  }
  this._refresh()
}
```

`_checkImpl`（`fiber.ts:597-609`）—— 找到就存进**本 fiber 的** `_store`：

```ts
_checkImpl(name: string) {
  const impl = this.ctx.reflect._getImpl(name, true)
  if (!impl) return delete this._store[name]
  try {
    if (impl.check && !impl.check.call(getTraceable(this.ctx, impl.value))) {
      return delete this._store[name]
    }
  } catch (error) {
    impl.fiber.ctx.logger.error(error)
    return delete this._store[name]
  }
  this._store[name] = impl        // ⭐ 这一步之后，Proxy 才找得到
}
```

> ⭐ **这就是「作用 2」的确切来源**：`inject` 里的每个名字 → `_checkImpl` → `this._store[name] = impl`。
> 「声明了 `inject`」和「`ctx.greeter` 能读到」是**同一条流水线的前后两站**。
>
> 顺带注意 `_store` 是 `Object.create(null)`（`fiber.ts:324`），**每个 fiber 一份，不是全局的** —— 所以 `child` 的 `_store` 是空的，它必须沿树向上找。

#### 机制一：门控靠 `epoch` 字符串

`vendor/cordis/src/fiber.ts:611-623`

```ts
_refresh() {
  let epoch: string | boolean = false
  epoch = ''
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) {
      epoch = INACTIVE                 // ← 缺任何一个依赖，直接判定「未激活」
      break
    }
    epoch += ':' + impl.fiber.uid      // ⭐ 记的是【提供方 fiber 的 uid】
  }
  this._setEpoch(epoch)
}
```

`_setEpoch`（`fiber.ts:625-639`）—— 决定往哪个方向走：

```ts
private _setEpoch(epoch: string) {
  const oldEpoch = this._runner.epoch
  if (epoch === oldEpoch) return              // ← epoch 没变就什么都不做
  this._runner.epoch = epoch
  if (this.inertia) return
  this._updateState(() => {
    if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
      this.inertia = this._reload()           // 从未激活 → 激活：加载
      return FiberState.LOADING
    } else {
      this.inertia = this._unload()           // 其余一律走卸载
      return FiberState.UNLOADING
    }
  })
}
```

> ⚠️ 注意 `else` 分支是**兜底**：不只是「激活 → 未激活」，**只要 epoch 字符串变了且不是「从未激活到激活」那种转变，都会走 `_unload()`** —— 包括「激活 → 另一个提供方」。所以提供方换了 fiber，是**先卸后装**，不是原地刷新。
>
> 🚧 **这是推断，我没有实测**：我从这段代码推出了 `_unload()` → `_reload()` 的两步走法，但**没有打印过 fiber 的状态迁移**来佐证。实测到的只有「t=600 三个插件又跑了一遍」这个结果（见上方输出）。

> ⭐ **`epoch` 里带 `impl.fiber.uid` 是关键设计**：它记的不是「服务名有了没有」，而是「**是哪个 fiber 在提供**」。
>
> 所以提供方**换了个 fiber**（HMR 重载、`dispose()` 后重挂）→ `epoch` 字符串变了 → **依赖方重新 `apply`**。
> 这就是上面 t=600 那一段三个插件重跑的原因，也是 [第 6 章 HMR](06-组合与-HMR.md#63-hmr改文件就重载) 能把插件热替换掉的基础。

#### 机制二：`ctx.greeter` 是 Proxy，找不到就沿树向上走

`vendor/cordis/src/reflect.ts:135-171`（`ReflectService.handler.get`，为聚焦起见只留了 `get` 这一支）

```ts
static handler: ProxyHandler<Context> = {
  get: (target, prop, ctx: Context) => {
    if (isSpecialProperty(prop)) {
      return Reflect.get(target, prop, ctx)
    }
    if (Reflect.has(target, prop)) {
      return getTraceable(ctx, Reflect.get(target, prop, ctx))
    }

    const error = new Error(`cannot get property "${prop}" without inject`)

    try {
      const def = target.reflect.props[prop]
      if (def?.type === 'accessor') {
        return def.get.call(ctx, ctx[symbols.receiver], error)
      }

      if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)
      return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
        const key = target[symbols.isolate][prop]
        let fiber = (ctx[symbols.shadow] as Context ?? ctx).fiber
        while (true) {                                     // ⭐ 沿 ctx 树向上找
          const impl = fiber.store?.[prop]
          if (impl) return getTraceable(ctx, impl.value)   // 找到就用
          if (prop in fiber.inject) {                      // 祖先声明了但还没就绪
            error.message = `cannot get required service "${prop}" in inactive context`
            throw error
          }
          if (!fiber.runtime) throw error                  // ← 走到根还没找到 → 抛
          if (fiber.parent[symbols.isolate][prop] !== key) throw error   // ⭐ isolate 边界
          fiber = fiber.parent.fiber
        }
      })
    } catch (e: any) {
      throw e === error ? enhanceError(e) : e
    }
  },
```

**三个要点**：

1. **`inject` 的产物是 `fiber.store[prop]`**（见上方「机制零」）—— 所以「声明了 inject」和「`ctx.greeter` 能读到」是**同一条流水线的前后两站**，不是两套机制
2. **查找沿 ctx 树向上冒泡** —— 这就是 `child` 没写 `inject` 也能访问的原因：它自己的 `store` 是空的，但父 fiber 的 `store` 里有
3. **`fiber.parent[isolate][prop] !== key` 在 isolate 边界处截断** —— 说明 `isolate` 不只给服务名换个 Symbol，**向上查找也会在那里停下**
   🚧 **这是推断，我没有实测**。它和 [6.1](06-组合与-HMR.md#61-条目的元数据) 那个 `isolate` 实验是**两个不同的结论**：那个实验证明的是「各拿一份实例」，这一条讲的是「查找不会跨过边界」—— 后者只在源码里见到。

> ⚠️ **错误信息 `cannot get property "X" without inject` 是有误导性的**。它的实际含义不是「你没写 inject」，而是「**查找链走到根了还是没找到**」。

### 🧪 实验：写法 ② 的「永远错过」是真的吗？

上面 `poll.ts` 就是这个实验，输出已经在上面的完整输出里。把它单独拎出来看时间线：

| 时刻 | 事件 | `ctx.get('greeter')` |
|---|---|---|
| t=0 | 还没有提供方 | `undefined` |
| t=300 | 提供方 ACTIVE | `object` |
| t=500 | 提供方已卸载 | `undefined` |
| t=700 | 提供方重新挂载 | `object` |

**结论：`ctx.get` 是纯粹的「读当前值」。**

- 它**不做任何等待** —— 没有就返回 `undefined`，不会卡住
- 它**不留下任何「我在等」的记录** —— 所以提供方后来出现时，**没有任何机制会来通知你**
- 它**不受 `inject` 门控** —— 这正是它的用途（读 `inject` 之外的东西）

> **「永远错过」的准确含义**：如果你在 `apply` 里**只读一次**并把它存下来（很自然的写法），那么提供方晚到时你**不会被唤醒**，手里永远是那个 `undefined`。要在这种场景下响应，用写法 ① 或 ③。

源码依据（`vendor/cordis/src/reflect.ts:233-243`）—— 注意第一句注释就直接说明了它的定位：

```ts
/**
 * Read a service from the store without the inject requirement.
 *
 * @param strict — when `true`, only return implementations whose providing
 *   fiber is currently active.
 * @returns the service value, or `undefined` when not (yet) provided.
 */
get(name: string, strict = true) {
  return getTraceable(this.ctx, this._getImpl(name, strict)?.value)
}

_getImpl(name: string, strict = true) {
  const key = this.ctx[symbols.isolate][name]
  const impl = key && this.store[key]
  if (!impl) return                                   // ← 没提供 → undefined
  if (strict && impl.fiber.state !== FiberState.ACTIVE) return   // ← 提供方还没 ACTIVE → undefined
  return impl
}
```

⚠️ 顺带注意 `_getImpl` **没有向上查找** —— 它只读 `this.store`（当前 reflect 的 store），不像 Proxy 那样沿 ctx 树冒泡。**这是 `ctx.get` 和 `ctx.greeter` 的另一个差别。**

`ctx.get` 是**单次属性读取** —— 它不在 `reflect` 里留下任何「我在等这个服务」的记录。而 `inject` 会（`notify()` 才有东西可唤醒）。

> 📌 注释里那句 `strict = true` 值得注意：默认情况下，**即使服务已经注册但提供方的 fiber 还不是 ACTIVE，`ctx.get` 也返回 `undefined`** —— 这进一步说明它是「此刻能不能用」的**瞬时快照**，而不是「以后会不会有」的承诺。

**这条已经实测过了**：`06-inject-why/poll.ts` 就是「不写 `inject`、用 `ctx.get` 读」的版本。它在 t=300/700 能读到服务（因为它是**每次重新读**），但**服务卸载、重挂这一整套变化，它完全没有被通知** —— 那些时间点只反映它自己去问的时刻。对照组的 `parent` / `late` 则是被自动唤醒的。

> 所以差别不在「能不能读到」，而在**「会不会被叫醒」**。`ctx.get` 是你主动去问；`inject` 是它有事来找你。

## 3.4 ⭐ 实验：PENDING 是**静默**的

**理论**（教程原话）：

> 消费方会保持 PENDING，不输出任何内容，**既不崩溃，也不会只运行一部分**。处于 PENDING 的 fiber 也**不会让 Node 的事件循环保持活跃**，因此如果组合中没有其他运行项，进程会**静默地以状态码 0 退出**。

这一点非常反直觉：**失败是完全静默的**。

### 🧪 验证实验：只挂消费方，不挂提供方

## 3.5 ⭐ 实验：加载后仍会跟踪依赖（自设计）

**理论**（教程原话）：

> `inject` **并非一次性的启动检查**。如果应用运行期间所需服务消失……每个依赖插件也会**随之卸载**，并在服务恢复后**再次加载**。结合 effect（第 2 章），这能**防止运行中的消费方保留对不可用服务的引用**：依赖消失时，它自己的注册也会撤销。

### 🧪 验证实验：卸载提供方，再挂回来

**📄 文件** `01-learn-basics/examples/cordis-tutorial/03-retrack/dynamic.ts`

```ts
import type { Context } from '@deepseek-ai/cordis'
import * as Greeter from './greeter.ts'
import * as Consumer from './consumer.ts'

export const name = 'dynamic-demo'

const wait = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms))

export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setTimeout(async () => {
      console.log('[t=0]    挂载 provider + consumer')
      let provider = ctx.plugin(Greeter)
      ctx.plugin(Consumer)
      await wait(300)

      console.log('[t=300]  卸载 provider（consumer 应随之卸载）')
      await provider.dispose()
      await wait(300)

      console.log('[t=600]  重新挂载 provider（consumer 应重新加载）')
      provider = ctx.plugin(Greeter)
      await wait(300)

      console.log('[t=900]  结束')
      process.exit(0)
    }, 0)
    return () => clearTimeout(timer)
  })
}
```

（`greeter.ts` / `consumer.ts` 内容与 3.2 完全相同，拷到本目录。）

**📄 文件** `01-learn-basics/examples/cordis-tutorial/03-retrack/cordis.yml`

```yaml
- name: './dynamic.ts'
```

**▶️ 运行**

```sh
cd tmp/cordis-tutorial/03-retrack
node --import tsx ../../../vendor/cordis/bin.js
```

**输出**

```
[t=0]    挂载 provider + consumer
Hello, world!
[t=300]  卸载 provider（consumer 应随之卸载）
[t=600]  重新挂载 provider（consumer 应重新加载）
Hello, world!
[t=900]  结束
```

**结论**：`Hello, world!` 出现**两次**。

| 时刻 | 发生了什么 | 证据 |
|---|---|---|
| t=0 | provider 挂上 → consumer 自动加载 | 第 1 个 `Hello, world!` |
| t=300 | provider 卸载 → consumer **静默卸载** | 期间**没有报错** |
| t=600 | provider 重新挂上 → consumer **自动重新加载** | ⭐ 第 2 个 `Hello, world!` |

**关键在第 2 个 `Hello, world!`** —— 整个过程中**没有任何代码**重新挂载 consumer。我在 t=0 只调了一次 `ctx.plugin(Consumer)`，之后它自己消失了、又自己回来了。

> ⭐ 顺带印证了 [2.6 的判据](02-生命周期与-effect.md#26-最重要的实践你已经不需要写-ctxeffect-了)：consumer 的卸载**不需要我写任何清理代码**。它 `ctx.on` 过的东西、注册过的工具，全部自动撤销。这就是「依赖消失时，它自己的注册也会撤销」的字面含义。

### 这个设计的意义

场景：`shell` 服务被替换（卸载 `dsh-bash-local`，挂载另一个实现）。

```
❌ 没有这个机制：
   旧 shell 卸载 → consumer 仍持有旧引用 → 调用到已死对象 💥

✅ 有这个机制：
   旧 shell 卸载 → consumer 被卸载（所有注册一并撤销）
                → 新 shell 挂载 → consumer 重新加载，拿到新引用
```

> 🔗 **这是第 2 章 effect 机制的终极用途**。consumer **不可能**持有悬垂引用 —— 这是**结构性保证**，不是靠程序员记得清理。

教程原话总结：**「这也是配置中可以替换服务的原因」** —— 对应 architecture.md 那句「一次提供方替换改变整个产品」。

## 3.6 命名：扁平命名空间

**理论**（教程原话）：

> 每个应用中的服务名称共用一个**扁平命名空间**。请为自有服务添加**有辨识度的前缀或命名空间**（harness 已占用 `tools` 和 `llm` 等普通名称）。

查全部已注册名字：子系统页面的 `cordis-surface` 区块。

> 🔗 **回扣 architecture.md 的包表** —— 这就是那个扁平命名空间的实际内容：

| 包 | `ctx` 键 |
|---|---|
| `core/session` | `ctx.sessions` |
| `core/system-prompt` | `ctx.systemPrompt` |
| `core/tools` | `ctx.tools` |
| `core/agent` | `ctx.agents` |
| `core/agent-loop` | `ctx.agentLoop` |
| `llm/llm` | `ctx.llm` |
| `webhook/webhook` | `ctx.webhookRuntime` |

> ⚠️ **「扁平」的代价**：`hello`、`stats`、`greeter` 这些名字**没有任何命名空间保护**。两个插件都想叫 `greeter` 就会撞车。
>
> **撞车时的规矩**（实测见 [6.5 服务名撞车](06-组合与-HMR.md#65-服务名撞车先注册的胜出后注册的静默-failed)）：
>
> - ✅ **先注册的胜出**
> - ❌ 后注册的那个 fiber 变成 `FAILED`
> - ⚠️ 而且**一声不响**：没有日志、没有异常、退出码 0
>
> 最容易误导人的地方：后注册的插件的 `apply` **确实跑了**（`console.log` 照样打印），
> 失败的只是它的 `<Service>` fiber —— 所以在启动日志上看不出任何异常。
>
> 这就是教程要求你加前缀的原因。

## 3.7 自测

**Q1**：把 `greeter.ts` 里的 `declare module { ... }` 整块删掉，会发生什么？

<details>
<summary>参考答案</summary>

**分两层看**：

- **运行时**：**照常工作** —— `super(ctx, 'greeter')` 仍然注册了服务，`ctx.greeter` 仍然能访问到
- **编译期**：`consumer.ts` 里的 `ctx.greeter` **类型报错** —— `Context` 接口上没有 `greeter` 这个属性

教程原话：「没有该声明时，服务在运行时仍能工作，但消费方会失去类型安全。」

**备注**：因为 `tsx` 不做类型检查，我们的实验即使删掉它也能跑出 `Hello, world!`。要看到报错得跑 `tsc`。

</details>

**Q2**：我要写一个插件，它在 `settings` 存在时注册一个设置项，不存在时**也要正常工作**（用默认值）。三种写法选哪个？

<details>
<summary>参考答案</summary>

**① `export const inject = ['settings']`** ❌ —— 服务缺失时整个插件不加载，不满足「也要正常工作」

**② `ctx.get('settings')`** ❌ —— 能优雅降级，但如果 settings 比本插件**晚加载**，就永远注册不上了

**③ `ctx.inject(['settings'], cb)`** ✅ —— 主插件照常运行（不阻塞），分店响应式等待。settings 早到晚到都能正确注册。

这正是 `agent-default-model` 的选择。

**为什么 ① 不行**：跑一遍 `03-service-consumer-only/` 就懂了 —— 你得到的不是「降级运行」，而是**整个插件一行都不执行**。写法 ① 没有「降级」这个选项，只有「全有」和「全无」。

</details>

**Q3**：为什么服务消失时，consumer 必须**被卸载**？让它继续跑、等下次调用时再检查不行吗？

<details>
<summary>参考答案</summary>

因为「下次调用时检查」会带来三种问题：

1. **悬垂引用**：consumer 闭包里可能已经捕获了旧的 service 实例。即使运行时能检测到失效，已经**注册出去的东西**（事件监听器、工具、路由）仍指向旧实现
2. **状态不一致**：consumer 可能有基于旧服务建立的内部状态，切换提供方后这些状态失去意义
3. **每个消费点都要写防御代码**：`ctx.shell?.run(...)` 到处都是，且很容易漏掉一个

而「卸载 → 重新加载」是**一次性、彻底、结构化**的：

- 所有注册通过 effect 自动撤销（第 2 章）
- 重新加载时 `apply` 从头执行，拿到的一定是新引用
- 消费方**一行防御代码都不用写**

**自己验证**：`03-retrack/` 的第 2 个 `Hello, world!` 就是证据 —— 重新加载后的 `apply` 是**从头执行**的，`ctx.greeter` 一定是新实例。

> **这正是「可逆副作用」这个设计的回报** —— 因为注册天生可撤销，「重新加载」才是廉价且安全的操作。如果注册是不可撤销的，这个机制根本无法实现。

</details>

---

**本章一句话总结**：

> 服务让插件**依赖一个名字，而不是一个实现**；`inject` 让这个依赖**持续有效** —— 不只是启动时检查一次，而是服务在则我在、服务走则我走、服务回来我回来。
