# acp：Agent Client Protocol 服务器

> 相关代码：`packages/acp`、[demo/acp-mini-client.mjs](../../demo/acp-mini-client.mjs)

headless 是「跑完就散伙」，那 ACP 就是「住下来聊」。它的全称是 Agent Client Protocol，通俗讲就是**给 IDE / 编辑器 / 宿主程序准备的接口**。你把 DSH 当后台引擎，编辑器是老板，agent 按老板的规矩干活。

对应关系一句话：**headless = 一次性，acp = 长会话**。DSH 的 ACP 实现是一个 `acp-demo` bin，spawn 起来后走 stdin/stdout 的行帧 JSON-RPC 协议。

## 是什么

ACP 让宿主程序（比如 Claude Code、Codex 之类的编辑器 agent）通过标准协议调起 DSH、建立会话、流式收发消息。对应关系：headless = 一次性；acp = 长会话。

## 怎么用（运行 demo）

[demo/acp-mini-client.mjs](../../demo/acp-mini-client.mjs) 是零依赖的最小客户端，spawn 一个 dsh-acp 服务器子进程，然后走完整协议：

```bash
node demo/acp-mini-client.mjs "用一句话回答：DSH ACP模式是什么？"
```

（脚本在 deepseek-harness 根目录运行，已同步到其 `demo/`）

## demo 代码说明

**第一步，spawn 服务器。** 服务器入口是 acp-demo bin，配置指向 `demo/cordis.local.yml`（仓库原配置去掉 thinking + 模型改成 deepseek-v4-flash）：

```js
const child = spawn(process.execPath, ['--import', 'tsx', ACP_BIN, '--config', ACP_CONFIG], {
  cwd: process.cwd(),
  env: { ...process.env, DEEPSEEK_BASE_URL: '...', DSH_PERMISSION_MODE: 'danger-full-access' },
  stdio: ['pipe', 'pipe', 'inherit'],
})
```

注意一个关键坑（写在脚本注释里）：**不要在 spawn 环境里塞占位 `DEEPSEEK_API_KEY`**。acp-demo bin 的 `loadEnv` 会加载根 `.env`，**且不覆盖已存在的环境变量**——传了占位 key 会抢走 `.env` 里的真 key（401）。环境里没有 key 时，脚本会从 `~/.dsh/.credentials.yaml` 全局凭据借真 key（acp 组合本身不挂 credentials 服务），`...process.env` 原样带过去。

**第二步，行帧 JSON-RPC 收发。** 协议走 stdin/stdout，每行一个 JSON：

```js
function request(method, params) {
  const id = ++nextId
  child.stdin.write(JSON.stringify({ id, method, params }) + '\n')
  return new Promise((resolve) => pending.set(id, resolve))
}
```

**第三步，协议四步走。** 这是 ACP 和 headless 最大的区别——它**显式建会话**：

```js
const init = await request('initialize', { protocolVersion: 1, clientCapabilities: {}, clientInfo: {...} })
const created = await request('session/new', { cwd: process.cwd(), additionalDirectories: [], mcpServers: [] })
const sessionId = created.result?.sessionId
const done = await request('session/prompt', { sessionId, prompt: [{ type: 'text', text: task }] })
console.log('stopReason =', done.result?.stopReason)
```

**第四步，处理流式事件。** ACP 桥把模型增量放在 `update.content`（text 块），**不是** `update.message.content`。字段路径必须按协议桥的实际实现取：

```js
const u = frame.params?.update
const kind = u?.sessionUpdate
if (kind === 'agent_message_chunk') {
  const block = u.content
  const text = typeof block === 'string' ? block : block?.text
  if (text) process.stdout.write(text)
}
```

## 自定义模型配置（当时改的三处）

连本地网关时，[demo/cordis.local.yml](../../demo/cordis.local.yml) 是 [examples/acp-agent/cordis.yml](../../examples/acp-agent/cordis.yml) 的本地副本，头部注释记录了当时的三处改动：

1. **url（网关地址）**：`DEEPSEEK_BASE_URL` 由启动环境提供（bootstrap-only，不能放 `.env`），`acp-mini-client.mjs` 从环境变量读取后透传给子进程。换网关改环境变量即可。
2. **key**：根 `.env` 提供 `DEEPSEEK_API_KEY`，由 acp-demo bin 的 `loadEnv` 加载。注意不能传占位 key（会抢走真 key）；没有 `.env` 时脚本从 `~/.dsh/.credentials.yaml` 借真 key。
3. **模型名称**：cordis.local.yml 里改两处——
   - `llm-deepseek` 的 `models` 列表列了网关认识的模型 id：

     ```yaml
     - id: llm-deepseek
       name: '@deepseek-ai/dsh-llm-deepseek'
       config:
         thinking: disabled
         models:
           - id: deepseek-v4-flash
           - id: deepseek-v4-pro
     ```

   - `acp-agent` 的 `model: deepseek-v4-flash`（网关只认识这个模型 id）：

     ```yaml
     - id: acp-agent
       name: '@deepseek-ai/dsh-acp-demo'
       config:
         provider: deepseek-official
         model: deepseek-v4-flash
     ```

配置文件里同时把 `thinking` 关掉了（Reasoning-ONLY 问题在 jsonrpc 篇详述）。

## 协议流程（四步）

`acp-mini-client.mjs` 里完整展示了四个步骤：

1. **initialize**：`{ protocolVersion: 1, clientCapabilities, clientInfo }`，握手拿 `agentInfo`。
2. **session/new**：`{ cwd, additionalDirectories, mcpServers }`，创建会话，拿 `sessionId`（响应 `result.sessionId`，没有 `session` 包装）。
3. **session/prompt**：`{ sessionId, prompt: [{ type: 'text', text }] }`，流式返回，结束时拿到 `stopReason`。
4. **收尾**：关掉 stdin（EOF）让服务器清盘退出。

## 执行结果输出

实跑（key 来自 `~/.dsh/.credentials.yaml` 全局凭据）：

```bash
node demo/acp-mini-client.mjs "用一句话回答：DSH ACP模式是什么？"
```

四步协议各打印一个阶段行，流式增量逐块拼成正文，最后以 `stopReason` 收尾：

```
① initialize → 服务器: deepseek-harness-acp
② session/new → sessionId: c8f01da1-150b-4f7e-9f01-29f69b13955c
③ session/prompt → 「用一句话回答：DSH ACP模式是什么？」
   模型回答（流式）: DSH ACP模式是DeepSeek Harness提供的基于Agent Client Protocol的自动化专用服务端模式（`packages/acp`），用于让外部客户端通过ACP协议无人值守地驱动agent运行。
④ prompt 完成，stopReason = end_turn
```

`sessionId` 每次运行不同；正文从 `agent_message_chunk` 的 `update.content.text` 增量拼出；`stopReason = end_turn` 即模型认为回答完整，无需客户端自行判定完成。

## 踩过的坑

**不要在 spawn 环境里塞占位 API key。** acp-demo bin 的 `loadEnv` 会加载根 `.env`，**且不覆盖已存在的环境变量**——如果传了占位 key，会抢走 `.env` 里的真 key，导致 401。正确做法是 `...process.env` 原样带过去（或从全局凭据借真 key），让 loadEnv 从根 `.env` 加载真 key。

**模型增量字段路径读错 → 一直没输出 → 调试 session 定位。** 最初跑 demo 时模型一直在生成，但终端里没有任何文字，以为是连接问题。逐帧打印 `session.event` 的事件后才发现，字段路径读错了：ACP 桥把模型增量放在 `update.content`（text 块），不是直觉上的 `update.message.content`。客户端组装输出时要按协议桥的实际路径取字段——定位办法就是把收到的每一帧 JSON 打印出来，对着实际结构找增量在哪。

**session/new 的响应结构。** 响应是 `result.sessionId` 直接给出，不是 `result.session.sessionId`（ACP 规范文档的示例与 dsh 实际实现有差异）。写客户端时先打印原始帧，别按文档猜。

**DEEPSEEK_BASE_URL 同样是 bootstrap-only。** 和 headless 一样，必须在 env 里显式传入，不能放 `.env`。

## 验证方式

- 协议层面：能看到 initialize → session/new → session/prompt 四步的响应，`stopReason` 非空即成功。
- 流式输出：客户端从 `agent_message_chunk` 增量里逐个打印 text，看到完整回答即验证流式通路。
- 会话保持：连续两次 `session/prompt` 用同一 `sessionId`，第二次能引用第一次的上下文。

## 使用场景

- 把 DSH 当作**后台 agent 引擎**集成进编辑器/IDE。
- 宿主程序需要**会话化**的 agent 能力（多轮、持久）。
- 需要协议级权限协商（ACP 桥的权限请求可以自动放行或转发给宿主确认）。

## 特点

- **会话化**：`session/new` 显式建会话，`sessionId` 贯穿多轮。
- **协议标准化**：宿主与 agent 之间走标准 ACP 握手，可替换实现。
- **流式 + stopReason**：prompt 直接返回完成原因，客户端无需自行判定。
- **与 headless 的对比**：headless 是一次性无会话；acp 是宿主驱动的长会话。
