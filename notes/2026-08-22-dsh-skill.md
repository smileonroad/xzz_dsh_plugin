# 2026-08-22 — dsh 的 skill 系统，官方真身长什么样

## 事情是这样的

前几篇练插件时产生了一个问题，dsh 能不能调 skill。直觉上觉得 dsh 一个 harness，估计没有这个能力，或者就算有也是个边角料。带着疑问去源码里翻了一下，结论完全相反，dsh 不但有，而且是一套完整的体系。

`packages/` 下有一个专门放 skill 的目录，里面四个包分工明确，有注册表、有文件系统 provider、有面向模型的加载工具，还有 web 界面的技能引用。这不是边角料，是一等公民。

更值得记的是，这四个包的分工，跟刚练完的 units-capability 几乎一模一样。这个故事可以从这个对比讲起。

## 背景，刚练完的 seam

这周在练 dsh 插件开发，写到第四个实战 units-capability，一个单位换算能力，练的是多插件协作。

核心认知是插件禁止互相 import，只通过服务键耦合。因为插件是热插拔的，A 直接 import B 就会焊死，B 一卸载 A 就崩。用服务键，A 只依赖「一个叫 units 的东西存在」，不关心谁提供、怎么提供。所以一个能力天然就是一个带三个角色的 seam，Definition 管契约、Provider 管数据、Consumer 管消费。

当时写这套时最大的感受是分工干净。想换数据，改一行配置，工具一字不用动。测试里把内置 provider 换成配置 provider，同一个 unit_convert 一行没改，单位表整个换掉，连温度的仿射偏移都算得对，零度摄氏换华氏是 32 度。10 个用例全过。

## 翻源码，撞见官方同款

带着「dsh 能不能调 skill」这个问题翻到 packages/skill 目录，第一眼是四个包的名字，dsh-skill、dsh-skill-filesystem、dsh-skill-badge、dsh-tool-skill。

打开 dsh-skill 的源码，第一行注释写着 Agent skill provider registry，负责合并各 provider 的目录、按名字解析胜出者、对外暴露摘要和定义。再看那个类，SkillRegistry extends Service，构造函数里 super(ctx, 'skills')。

这正是刚写过的 UnitsService extends Service、super(ctx, 'units')，骨架一模一样。

dsh-skill-filesystem 就是 provider，从磁盘上发现技能。它按优先级扫一串目录，项目里的 .dsh/skills、用户目录下的 ~/.dsh/skills、~/.agents/skills，最后是内置的 bundled 目录，每个来源一个 rank，rank 小的赢。同名时也有规矩，项目里的优先、运行时注册的次之、用户目录的再次、内置的垫底。技能在磁盘上的格式是目录 bundle，一个技能一个文件夹，正文叫 SKILL.md。

这个 SKILL.md 每天都在用，本会话挂的一堆技能（lark 那一系、ljg 那一系、rw 那一系）全是从 ~/.agents/skills 发现的，数了一下 78 个目录。原来一直在用的东西，底下就是这套架构。

dsh-tool-skill 注册的工具名字就叫 skill，description 是加载一个可用技能的完整指令。每次任务匹配到某个技能，就调一次这个工具，把技能全文加载进上下文再执行。这个工具的本体，就是 packages/skill 里这几百行代码。它还顺带发布一个会话技能目录，就是系统提示里那个 available_skills 列表。

用户侧也有一条路，web 输入框注册了斜杠技能引用源，用户可显式触发技能，宿主把技能正文以 instructions 形式注入会话。每个技能还有 modelInvocable 和 userInvocable 两个开关，分别控制模型和用户能否调用。

四条调用路径，模型一条、用户一条、provider 一堆、注册表一个，跟练的那个 seam 角色数量对得上。

## 沙箱插曲，vitest 的 spawn EPERM

中间有个插曲。跑测试时 vitest 启动直接报 spawn EPERM，代码一行没动。排查发现是沙箱的问题，dsh 的文件沙箱在受限模式下禁止子进程用管道方式启动，vite 解析配置时要 spawn 一个子进程拿真实路径，被拒。判定条件很具体，子进程只要用管道方式接输出就会被拒，用继承或忽略的方式反而没事。把命令升级一次权限就过了。这个坑记下来，以后跑 vitest 前先确认沙箱权限。

## 先练一遍，再撞见官方真身

写到这想说一个跟代码无关的点。

分层、解耦、依赖倒置是软件工程常识，但如果先读架构文档，会觉得这只是标准做法。这次不一样的地方在于，先自己手写了一遍，然后才在官方源码里撞见同款。这个顺序很关键，先练过再看到官方真身，会意识到练的东西就是这门手艺的地基，不是写作业，是在练语感。

seam 这个套路，units 是它、skills 是它，dsh 里其他能力多半也是它。命令是一个 seam、工具是一个 seam、会话是一个 seam、agent 预设也是一个 seam，整座 harness 就是一堆 seam 互相咬合，每个都是注册表加 provider 加消费方，谁都不 import 谁，只认键。

这大概就是 Cordis 说「一切皆插件」的真正意思，不是什么东西都做成插件这么简单，而是所有能力都长成同一个形状，学会一个就学会全部。

## 接下来该干嘛

回到开头的问题，dsh 能不能调 skill。能，而且它跟练过的 seam 是同一个套路。

想验证这个发现的，可以翻一翻 packages 目录，挑一个练过的能力（commands、tools、skills 都行），看它的注册表怎么写、provider 怎么注册、消费方怎么 inject。从 skills 开始最合适，包最小，四个文件就能看明白，而且本机就有现成的技能目录可以对照。
